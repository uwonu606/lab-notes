## 판정 요약

### 답

이 말뭉치(개인 노트 3편, 57청크)에서는 "HippoRAG 2 + JonexWiki" 조합이 dense 기준선 A 보다 우연과 가를 만큼 낫다는 측정이 없다. 가장 가까운 것은 passage 가중치 1.0 재구현의 recall@5 0.863 인데, A 0.838 과 갈린 질문 3개 가운데 2개를 이긴 차이라 우연과 가를 수 없고 그때 순위는 사실상 dense 다(측정 4). 잰 지표 가운데 나아진 것은 둘뿐이다. 구조 질문 재현율은 사람이 용어집 항목 병합 3쌍을 승인했다고 스크립트로 흉내 낸 판에서만 올랐고, 원문 추적은 jonex 인용 규칙이 구조로 보장한다. 두 이득 모두 HippoRAG 2 의 그래프·PPR 없이 나온다. 그래서 물음에 대한 답은 "HippoRAG 2 고유 장치를 더해서는 나아지지 않았다. dense + 사람 용어집 + jonex 쓰기 규칙이 같은 이득을 더 싸게 낸다" 다. 사용자가 가장 원하는 "용어가 다른 쌍" 연결(지표 3)은 정답 쌍이 0개라 판정할 수 없고, 그래서 이 답은 사내 보고서로 옮기기 전에 다시 재야 하는 가설이다.

### 권하는 조합

권하는 조합은 "최소 차용" 을 검증에 맞춰 고친 판이다(#조합안 네 갈래와 검증 결과 의 "최소 차용"). 검증 세 관점 모두에서 치명적 결함이 나오지 않은 유일한 안이다.

- 찾기는 bge-m3 dense(A)와 사람이 관리하는 용어집 글자 매칭, Adamic-Adar 순위를 그대로 둔다.
- HippoRAG 2 에서는 동의어 선을 만드는 이름 cosine 계산만 빌린다. 선을 자동으로 달지 않고, 문턱을 미리 정한 "용어집 항목 병합 대기열" 로 사람에게 보낸다. 용어집 매칭이 0개인 대상에만 dense 를 쓰는 조건부 fallback 은 HippoRAG 2 의 "필터가 비면 dense" 와 모양만 같다(`HR/HippoRAG.py:762-764`).
- jonex(JonexWiki 엔진) 에서는 쓰기 규칙을 빌린다. 원문 그대로 발췌 확인(`JW/domain/engine/compile/understanding.py:576-584`), 문자 구간 고정(`JW/domain/engine/models/compiler_state.py:427-483`), `[E#]` handle 복원(`JW/domain/engine/query/synthesis_orchestration.py:719-757`), "조용히 버리지 않는다" 는 기록 원칙(`JW/domain/engine/compile/engine.py:75-80`)이다. 여기에 jonex 에 없는 "사람 판정 저장" 을 더한다.

이 조합에서 HippoRAG 2 고유 장치(passage 노드 그래프, PPR 전파, query-to-triple, recognition memory)의 몫은 0 이다. 그래서 결론은 "조합하지 않고 dense + 사람 용어집 + jonex 쓰기 규칙" 에 가깝다.

### 다른 조합을 고를 조건

| 조합 | 고를 조건 |
|---|---|
| 검색 핵심(HippoRAG 2 검색 + JonexWiki record 근거 층) | 공식 HippoRAG 2 패치판이 따로 둔 질문 절반과 약 300청크 규모 시험 모두에서 dense 를 평균 3문항 넘게 앞서고, 동시에 jonex record 묶음이 LLM 없는 문장 조각 묶음보다 글자 예산 재현율이 높을 때 |

## HippoRAG 2 는 무엇인가

### 색인과 검색 흐름

HippoRAG 2 는 Gutiérrez 외, "From RAG to Memory: Non-Parametric Continual Learning for Large Language Models"(arXiv 2502.14802, ICML 2025)다.

색인은 다음과 같다.

1. LLM 이 passage 마다 이름(NER)을 뽑고, 그 이름을 조건으로 (주어, 관계, 목적어) 트리플을 schema 없이 뽑는다(논문 §3.1, 논문txt:332-338). 공식 코드는 청크당 NER 1회 + 트리플 1회다(`HR/prompts/templates/ner.py:1-22`, `HR/prompts/templates/triple_extraction.py:1-50`).
2. 트리플의 주어·목적어 문자열이 phrase 노드가 된다. 같은 두 phrase 사이 트리플 수가 fact 선의 무게다(`HR/HippoRAG.py:1179-1228`).
3. passage 마다 passage 노드를 두고, 그 passage 에서 나온 모든 phrase 와 context 선(무게 1.0)으로 잇는다(논문 §3.2, `HR/HippoRAG.py:1230-1276`).
4. phrase 임베딩 cosine 이 0.8 이상인 쌍을 동의어 선으로 잇는다. 노드를 합치지는 않는다(논문 §3.1·표 13, `HR/HippoRAG.py:1278-1352`). 동의어 선은 MuSiQue 그래프에서 전체 선 1,399,367 개 중 1,125,951 개다(논문 표 10).

검색은 다음과 같다.

1. 질문 임베딩과 모든 트리플 임베딩을 견줘 상위 5개를 고른다(query-to-triple, 논문 §3.3·§4.4).
2. recognition memory: LLM 이 그 5개 가운데 관련된 것만 남긴다(논문 §3.4). 남은 것이 없으면 그래프를 쓰지 않고 dense 검색 결과를 돌려준다(논문 §3.5, `HR/HippoRAG.py:762-764`).
3. 남은 트리플의 phrase 최대 5개와 모든 passage 노드를 PPR 시작점으로 둔다. passage 쪽은 질문-passage 유사도를 min-max 정규화한 뒤 0.05 를 곱한다(논문 부록 G.1, `HR/HippoRAG.py:2088-2098`). phrase 쪽은 트리플 점수를 그 phrase 가 나온 청크 수로 나눈다(`HR/HippoRAG.py:2063-2066`). 논문 v2 는 이 나눗셈을 적지 않았고, v1 은 이것을 node specificity 라고 불렀다.
4. 방향 없는 그래프에서 damping 0.5 로 PPR 을 돌리고(`HR/HippoRAG.py:2203-2212`), passage 노드 점수로 순위를 매겨 상위 5개를 답 모델에 넘긴다.

같은 명목 설정에서 두 판이 3문항 갈렸다. 동의어 선의 효과도 측정 3 에서는 −0.037, 측정 4 에서는 +0.037 로 부호가 반대다. 그래서 0.05 판의 숫자를 문항 단위 정밀도로 읽을 수 없다. 두 판 모두 dense 보다 낮다는 방향만 같다. 1.0 판은 dense 를 1~2문항 넘지만, A 와 갈린 질문이 셋뿐이다. 측정 4 에서 A 보다 나은 질문은 s17·b09 둘이고 못한 질문은 b12 하나다. 두 재구현에는 LLM 호출이 없어 다시 돌려도 숫자가 같으므로, 회차 13 의 "재실행 흔들림 1문항"(`ASK/notes.md:528`)은 여기 기준이 되지 못한다. 기준은 질문 표본의 크기이고, 갈린 3문항 중 2개를 이긴 것은 우연과 가를 수 없다(양쪽 확률이 같다면 3문항 중 2개 이상을 이길 확률이 0.5 다).

## jonex 방식의 요지와 HippoRAG 2 와의 접점·부딪힘

### 두 갈래 가운데 이 글이 쓰는 것

jonex 플랫폼은 KB 종류마다 두 길 중 하나로 문서를 보내고, 두 길은 서로 배타다(`llm-wiki-four-repos/lab/repos/yuezhiai_jonex/capabilities/knowledge_base/services/document_service.py:681-682`, `llm-wiki-implementations/lab/reports/schema-glossary/yuezhiai-jonex.md:5-8`).

| 갈래 | 무엇 |
|---|---|
| JonexWiki 엔진 (`kb_type=jonex_wiki`) | LLM 은 원문 발췌와 이름만 제안하고, 사실 판정·페이지·같은 대상·링크·인용은 코드가 정한다 |
| Ontology 그래프 길 (`kb_type=lightrag`) | 사람이 정한 TBox YAML 과 KB 별 동의어 묶음으로 엔티티·관계를 뽑아 Neo4j 에 쌓는다 |

이 글은 JonexWiki 엔진을 "jonex 의 방식" 으로 읽는다. 사용자가 jonex 에 대해 물은 열 가지가 모두 JonexWiki 엔진의 주장(claim)·passage·facts·페이지·LLM 쓰임에 관한 것이었고, Ontology 길의 TBox·Neo4j 는 묻지 않았기 때문이다(`llm-wiki-four-repos/notes.md:22-31`). Ontology 길에서는 "KB 단위 동의어 묶음" 이라는 저장 모양만 생각으로 빌린다. 우리 용어집 150개(`ASK/lab/inputs/12-glossary.json`)가 이미 그 자리에 있다. 사용자가 어느 갈래를 뜻했는지는 확인하지 않았다(#모르는 것과 물어야 할 것).

참고: 앞선 기록은 B3m 을 "jonex 식 대리" 로 읽었다. B3m 은 Ontology 길에 가까운 구성을 AutoSchemaKG 검색기로 돌린 것이라 JonexWiki 의 대리도, jonex Ontology 길의 대리도 아니다.

## 조합안 네 갈래와 검증 결과

검증은 세 관점에서 따로 했다. 하나는 기제 충실도(설계가 원래 동작을 정확히 옮겼고 그 효과가 따라오는가), 하나는 우리 측정과의 정합, 하나는 작은 모델·한국어·사용자 요구·비용·라이선스다. 세 관점의 판정이 갈리면 그렇다고 적는다.

### 검색 핵심: HippoRAG 2 검색 + JonexWiki record 근거 층

설계는 HippoRAG 2 그래프를 dense 순위 뒤의 보조 채널로 내리고, jonex 이해 호출(passage 당 1회)로 원문 발췌 record 를 만들어 "근거 묶음" 과 `[E#]` 인용의 단위로 쓴다. 근거 묶음은 dense 상위 5청크의 record 가운데 질문 cosine 이 "1위 청크 cosine − δ" 이상인 것을 먼저 싣고, 그 뒤 원문 청크를 채운다. 관계의 주어·대상이 그 record 발췌 안에 있을 때만 트리플로 쓰는 근거 검사를 새로 둔다. 동의어 선의 ASCII 조건을 풀고 0.85 위만 자동 선, 0.7~0.85 는 검토 로그로 보낸다.

살아남은 주장:

- 원래 설정을 옮기면 recall@5 가 dense 보다 낮다(측정 3 의 0.713). 두 재구현 모두 방향이 같다.
- passage 가중치 1.0 에서는 A 와 같아진다(측정 3 의 0.850, 동의어 없으면 0.838).
- 방향 없는 PPR 은 차수 높은 청크로 쏠린다. PPR 1위 청크의 평균 차수는 15.2 로 dense 1위 11.5 보다 높고(말뭉치 평균 12.5), 1위가 정답인 질문은 PPR 10/40, dense 25/40 이다(측정 5). 이 쏠림은 청크 수로 나누기를 켠 채 생겼다. 나누기는 phrase 시작점만 낮추고 차수 큰 passage 로 모이는 걸음은 막지 않는다.
- reset 정규화 때문에 0.05 를 우리 규모에 그대로 쓸 수 없다(측정 2, prpack.cpp 53-71행).
- 대리 record 는 질문 정답 단위 60개 중 27개(0.45), 구조 정답 단위 68개 중 25개(0.368)만 덮는다(측정 8). record 만으로 검색 단위를 대신할 수 없다.
- record 를 passage 노드로 넣으면 recall@5 가 0.600~0.613 으로 떨어진다(측정 3).
- jonex 는 발췌는 검사하지만 관계의 주어·대상 이름은 검사하지 않는다(`understanding.py:746-777`). 대리 데이터에서 양 끝이 청크에 그대로 있는 트리플은 415개 중 290개(69.9%)다(측정 8). 설계의 검사는 더 짧은 발췌 안에서 보므로 통과율은 이보다 낮을 것이다.
- 필터를 빼도 논문 다중 홉 recall@5 는 평균 0.7 만 떨어진다(표 4). 70B 필터 대비 값이다.
- jonex 키워드 검색은 한국어에서 쓸 수 없다(측정 16).

무너진 주장:

- "동의어 선을 켜든 끄든 차이는 1문항 안쪽" 은 반박됐다. passage 가중치 0.05 에서 0.713 대 0.750 으로 1.5문항 차이이고, 측정 4 에서는 부호가 반대(0.750 → 0.787)다. 작은 모델 관점의 검증은 이 주장을 지지했지만, 기제 관점과 측정 정합 관점이 같은 숫자로 반박했다.
- "이득은 jonex 근거 층에서 나온다" 는 대리 데이터에서 무너졌다. LLM 없이 정규식으로 자른 문장 조각 1,027개(평균 48.9자)를 같은 δ 규칙으로 실으면 1000자 재현율이 δ 0~0.15 에서 0.550/0.613/0.637/0.637/0.650/0.637 이다. 대리 record 는 0.550/0.588/0.588/0.575/0.562/0.613 이다(측정 7). 문장 조각이 모든 δ 에서 같거나 높다. 같은 범위가 나누기 크기만 바꿔도 이미 나온다(고정 800자 0.550, 고정 610자 0.562, gemma4 주제 경계 0.613, `ASK/lab/runs/21-eval-fixed-sweep.txt:15`, `ASK/lab/runs/21-eval.txt:19-24`).
- "5000자는 그대로" 는 δ 0.15 에서 깨진다(0.812, 측정 7). 2500자 이득은 짝수 절반(0.675 → 0.700~0.725)에서만 나오고 홀수 절반은 0 이다(측정 6).

치명적 결함(기제·측정 정합 관점): 앞 5자리를 dense 로 고정하므로 HippoRAG 2 는 recall@5 를 정의상 바꿀 수 없다. 성공 기준 "A 보다 0.025 넘게 낮지 않다" 는 그래프를 통째로 빼도 통과한다. 이 안이 이겨도 "dense + 짧은 조각 묶음 + `[E#]` 복원" 이 이긴 것이고, 조합 물음에 답하지 못한다. 작은 모델 관점은 치명적 결함을 들지 않았지만, 자동 선의 근거(용어집 이름 정밀도 0.780)가 OpenIE 이름에 옮겨지지 않는다고 지적했다. OpenIE 이름 cosine 0.9 이상 18쌍 중 12쌍이 포함 관계이고 `llms`↔`lms` 0.915, `apple iphone 15`↔`iphone 15` 0.973 같은 다른 대상이 섞여 있다(측정 14).

현실적 기대: recall@5 는 0.838 그대로다. 1000자 예산은 +0.08~0.14(0.475 → 0.550~0.613)지만 그 몫은 LLM 없는 문장 조각으로도 나온다. 원문 추적은 구조상 보장되지만 그래프 없이도 된다. 색인 호출 57~114회를 더한다.

### 링크 제안기: jonex 식 규칙 링크 위에 HippoRAG 2 동의어 선·PPR 을 검토 후보로

설계는 용어집 글자 매칭과 Adamic-Adar 순위로 링크를 확정하고(`ASK/lab/runs/18-eval.txt:4` P 0.44 R 1.00, `ASK/lab/runs/19-entry-weight.txt:12` P 0.52), HippoRAG 2 의 bge-m3 이름 cosine 과 PPR 이웃을 "용어 쌍 검토 항목" 과 "청크 쌍 검토 항목" 으로만 낸다. 사람이 "같음" 을 주면 별칭이 되어 링크가 코드로 다시 계산되고, 판정 장부에 남는다.

살아남은 주장:

- bge-m3 이름 cosine 띠별 "같음" 비율은 ≥0.9 0.92, [0.8, 0.9) 0.57, [0.7, 0.8) 0.42, [0.6, 0.7) 0.10 이다(측정 1 의 누적 셈을 띠로 뺌). 용어집 이름끼리의 대리 측정이다.
- 공식 동의어 선 코드는 ASCII 조건 때문에 한국어끼리 쌍을 후보로 만들지 못한다(`HR/HippoRAG.py:1333`).
- 승인한 별칭을 용어집에 넣으면 링크가 결정적으로 다시 계산되고, 별칭을 빼면 그것에 기댄 링크만 빠진다(`ASK/lab/reports/19-tentative-links.md:229-230`, `ASK/lab/18_glossary_grow.py:122-127`).
- 링크 시점에 생성 모델을 부르지 않아도 된다. 새 청크마다 이름 추출과 임베딩만 든다. 이름 추출은 공식 HippoRAG 2 OpenIE 로 하면 NER·트리플 2회이고, 이번 측정이 쓴 회차 13 의 entity_relation 단계로 하면 1회(llama3.1:8b 평균 9.25초)다(`ASK/lab/runs/12-cache/*.json` 의 usage).
- jonex 의 두 갈래는 KB 마다 배타라서, JonexWiki 규칙과 Ontology 길의 동의어 묶음을 함께 쓴 구성은 jonex 에 없다. 그 섞음의 성능 출처도 없다.

무너진 주장:

- "작은 모델 OpenIE 가 잇는 데 필요한 표면형을 낸다" 는 반박됐다. 연결 정답 25쌍 중 22쌍이 기대는 AutoSchemaKG 가 새 문서 phrase 에 한 번도 나오지 않았다. 새 문서 phrase 88개 중 87개는 새 문서에만 있다(측정 10).
- "별칭은 문맥과 무관하게 같은 대상을 가리킨다" 는 반박됐다. 새 문서 `doc-parsing-chunking#00` 의 "키워드·서지 수집" 은 서지 검색어 모으기인데(`ASK/lab/inputs/12-chunks.jsonl`), OpenIE 이름 `키워드 수집` 이 cosine 0.784 로 keyphrase extraction 항목의 별칭 `keyword extraction` 에 붙는다. 이 항목과 같은 0.7~0.8 띠의 다른 하나(`doclaynet`↔WordNet 0.703, 역시 다른 대상)를 승인하면 정답 밖 새·옛 청크 쌍 15개가 한꺼번에 생긴다(측정 10). 회차 17 에서 Sonnet 이 `keyphrase` ← `키워드` 별칭을 넣었을 때 같은 실패가 이미 있었다(`ASK/notes.md:738-739`).
- "우리 말뭉치에 용어가 다른 쌍이 충분하다" 는 반박됐다. 용어집 한 항목의 다른 표기로만 이어지는 쌍이 0개다(측정 9). 정답 25쌍의 subject 는 모두 AutoSchemaKG 이거나 autoschemakg 노트다(`ASK/lab/inputs/12-links.json`).
- "범용어가 PPR 경로를 독점하지 않는다" 는 반박됐다. 새·옛 문서가 공유한 phrase 는 `세션` 하나뿐이다. 동의어 선 없이 `#00` 이 닿은 옛 청크 38개가 모두 그 경로로 왔고, 나머지 새 청크 넷은 하나도 닿지 않았다(측정 10).
- "LLM 판정은 거름으로 쓰면 안 된다" 는 관점마다 갈렸다. Sonnet 판정이 정답 25쌍 중 18쌍을 버린 숫자(P 0.64 R 0.28, `ASK/lab/runs/20-rerank.txt:7`)는 맞다. 하지만 측정 정합 관점은 그 18쌍이 정답 기준("같은 이름이 양쪽에", `ASK/notes.md:121`)과 판정 기준("같은 것을 다룬다")이 어긋난 결과라고 반박했다(`ASK/notes.md:805`). 그래서 이 주장은 결론에 쓰지 않는다.
- "PPR 이웃이 dense 이웃보다 낫다" 는 근거가 없다. 상위 3 에서 PPR 1 대 dense 2, 상위 5 에서 3 대 3, 상위 10 에서 11 대 5 다(측정 10). k 에 따라 갈리고, 상위 10 의 우세는 범용어 `세션` 경로를 거친 우연일 수 있다.
- "사람이 용어 쌍 하나를 판정하는 시간이 청크 쌍 하나보다 짧다", "벡터 후보를 더해도 증명될 때만 규칙이 깨지지 않는다" 는 잰 출처가 없다.

치명적 결함(기제·측정 정합 관점): 이 말뭉치에서 노리는 현상이 0건이고, 실제로 나온 후보는 모두 틀렸다. "새 청크당 검토 항목 0.4~7.8개가 용어집 후보 전부 11.4개보다 적다" 는 비교도 성립하지 않는다. 11.4 는 정답 25쌍을 모두 담은 목록이고, 0.4~7.8 은 정답을 하나도 담지 않은 목록이다. HippoRAG 2 에서 실제로 가져온 것은 bge-m3 이름 cosine kNN 하나라, 사실상 권하는 조합의 대기열과 같다.

현실적 기대: 이 말뭉치에서 새로 맞는 연결은 0쌍이다. 링크마다 원문 구간과 판정 장부를 남기고 승인 한 줄로 되돌리는 구조만 확인된다.

### 최소 차용 (권하는 조합의 바탕)

설계는 dense 와 용어집은 그대로 두고, HippoRAG 2 의 이름 cosine 을 용어집 항목 병합 대기열로, dense fallback 을 "용어집 매칭이 빈 대상에만" 으로, JonexWiki 의 발췌 원문 확인을 답 인용에 건다. PPR·query-to-triple·recognition memory·자동 동의어 선은 빌리지 않는다.

살아남은 주장:

- 새 문서 연결에서 PPR(동의어 포함) 상위 5 제안은 R 0.12 P 0.12 이고, 용어집 글자 매칭은 57쌍 중 25쌍 정답이다(측정 10, `ASK/lab/runs/18-eval.txt:4`).
- HippoRAG 2 의 흔한 phrase 보정(1/df)으로 연결 후보를 매기면 Adamic-Adar 와 같은 곡선이다. 재현율 1.00 에서 최고 정밀도 0.52(48쌍)다(측정 15).
- 항목끼리 cosine 에서 rebase·amend·ultra-fine typing 은 짝인 긴 이름 항목의 이웃 1위다(0.846·0.735·0.902). UFET 는 Choi 2018 의 이웃 27위(0.508)다. 대기열은 문턱 0.65 에서 113쌍, 0.7 에서 61쌍, 0.75 에서 33쌍이고 알려진 4쌍 중 3·3·2쌍을 담는다(측정 11).
- 회차 22 의 구조 질문 빈칸은 기존 용어집이 rebase·amend·UFET·ultra-fine typing 을 git rebase·git commit --amend·Choi 2018 과 다른 항목으로 두어서 생겼다(`ASK/lab/runs/22-glossary-기존.json`, `ASK/lab/22_alias_fill.py:13`).
- 승인 3쌍과 조건부 fallback 을 쓰면 구조 정밀도/재현율이 고정 1000자에서 0.79/0.90 이고, 다른 나누기 다섯을 합한 여섯 판에서 0.75~0.85 / 0.89~0.95 다(측정 11). 다만 정밀도 상승은 평균 방식에서 생겼다. 기준 0.58 은 맞힌 대상 7개의 평균 0.83 에 7/10 을 곱한 값이다(빈 대상 3개를 0 으로 셈, `ASK/lab/runs/22-eval.txt:65-74`). 맞힌 대상 기준 정밀도는 0.83 에서 0.85 로 거의 그대로다.
- 작은 판정기는 대기열을 자동 승인하지 못한다. 0.6~0.8 띠에서 gemma4:e2b 는 표본 정밀도 0.926 이지만 재현율 0.275, llama3.1:8b 는 0.857 / 0.330 이고, exaone3.5:2.4b 는 182쌍 모두에 No 라고 답했다(측정 12).
- llama3.1:8b 에게 dense 상위 5 와 원문 그대로 인용 지시를 주면 JSON 40/40 이 읽힌다. 인용 51개 중 41개가 원문 확인을 통과하고, 모든 인용이 통과한 답은 32/40 이다(측정 13).
- llama3.1:8b 가 뽑은 이름은 83.5%(828개 중 691개)만 자기 청크에 글자 그대로 있다(측정 14). 그래서 LLM 추출 이름을 후보로 쓰려면 원문 확인부터 해야 한다.
- 발췌 확인은 공백만 정규화한 부분 문자열 검사라 한국어에 쓸 수 있고, 지지 판정의 토큰 규칙은 한글을 버리므로 빌리지 않는다.

무너진 주장:

- "공식 seed 규칙에서 0.05 판이 0.750" 은 판 이름이 틀렸다. 0.750 은 동의어 선을 뺀 판이다. 공식처럼 동의어 0.8 + 청크 수로 나누기를 쓰면 0.787(26/40)이다(측정 4). 측정 정합 관점이 반박했고, 다른 두 관점은 숫자를 지지하며 같은 정정을 붙였다.
- "청크 수로 나누는 보정은 늘 나누지 않은 판 이상" 은 반박됐다. 용어집 그래프 PPR 에서 passage 가중치 1.0 일 때 나눈 판 0.800, 나누지 않은 판 0.812 다(측정 15).
- "57청크에서는 passage 몫이 0.19~0.53 으로 커진다" 는 방향이 거꾸로다(기제 관점의 반박). 큰 말뭉치에서 passage 몫이 0.98 이상이므로 57청크의 값은 작아진 것이고, 그만큼 phrase 쪽 몫이 커진다(측정 2). "논문 값을 옮겨 읽으면 안 된다" 는 결론은 남는다.
- "40문항 recall@5 의 우연 흔들림은 3~4문항" 은 근거가 없다. 같은 그래프 재실행 흔들림은 1문항이고(`ASK/notes.md:528`), 0.738~0.838 은 청크 크기를 바꾼 체계적 차이다(`ASK/notes.md:856`). 구현을 바꾼 차이는 약 3문항이었다(측정 3·4).

치명적 결함은 세 관점 모두 들지 않았다. 고칠 것은 아래 일곱이다. 권하는 조합은 이것을 반영한 판이다.

1. 필수: 구조 재현율 0.63 → 0.86~0.90 은 이미 별개 항목으로 있던 짧은 꼴을 합친 값이다. 실제 보고서에서 기대야 할 "용어집에 없는 새 이름 → 항목" 대기열(후보 이름 739개, 0.7 에서 195쌍)은 알려진 빈칸 4개를 담을 수 없게 짜였다. 4개 모두 이미 용어집 항목이라 후보에서 빠졌다(측정 11). 그래서 이 경로의 성능은 0 이 아니라 미측정이고, 바꿔 쓰기 사본에서 따로 재야 한다.
2. 필수: 승인 3쌍은 정답을 보고 골랐고 문턱 0.7 도 결과를 본 뒤 정했다. 문턱을 미리 정하고, 검토자는 정답을 보지 않는다.
3. 정밀도는 "맞힌 대상 평균" 과 "빈 대상 수" 로 나눠 보고한다.
4. 승인 1건당 볼 쌍 수는 0.7 에서 61/3 = 20.3, 0.65 에서 37.7, 0.75 에서 16.5 다(측정 11). 설계의 성공 기준 "20쌍 이하" 를 이미 넘는다. "항목마다 가장 가까운 항목 하나만" 으로 자른 판을 먼저 잰다.
5. gemma4 자동 별칭 제안(사람 없음)이 이미 고정 1000자 별칭 매칭 0.75/0.79 였다(`ASK/lab/runs/22-eval.txt:47`). 대기열의 몫은 이 판 대비 재현율 +0.07~0.11 이다. 이 판을 비교군에 넣어 사람 개입의 값을 잰다.
6. 원문 확인 성공 기준 80% 는 지금 값(41/51 = 0.80)과 같아 기준이 되지 못한다. 자유 형식 인용 판과의 짝 비교로 바꾼다.
7. dense fallback 은 HippoRAG 2 가 필터가 빌 때 쓰는 안전장치이고 성능 부품으로 ablation 된 적이 없다. 차용 근거를 "모양만 같다" 로 낮춘다.

### 작은 모델 우선: 작은 모델은 이름 뽑기·예/아니오·답 한 번만

설계는 LLM 호출을 셋으로 줄인다. llama3.1:8b 가 청크마다 이름을 한 번 뽑고, gemma4:e2b 가 애매한 이름 쌍에 예/아니오를 답하고, llama3.1:8b 가 답을 한 번 쓴다. 공식 HippoRAG 2 사본을 패치해 그래프를 짓고, 트리플 양 끝이 원문에 있을 때만 넣는다. 0.9 이상은 자동 선, 0.7~0.9 는 코드로 먼저 막고(숫자가 다르면, 한 이름이 다른 이름을 품으면, 원문이 관계로 밝히면) 남은 쌍을 gemma4 가 판정한다.

살아남은 주장:

- bge-m3 0.8 문턱은 같은 대상 221쌍 중 57쌍(0.258)만 잇고 정밀도 0.671, 0.9 문턱은 22쌍(0.100)에 정밀도 0.917 이다(측정 1).
- 공식 ASCII 조건은 llama 이름 603개 중 118개를 빼고 그중 112개가 한글을 품는다. 유니코드 글자 2자 이상으로 바꾸면 3개만 빠진다(측정 14).
- 필터 후보와 NER 결과에 `ensure_ascii` 가 없다(`HR/rerank.py:111`, `HR/information_extraction/openie_openai.py:140`).
- 트리플 두 끝이 원문에 그대로 있는 비율은 70.3%(291/414)다. 근거 검사를 통과한 트리플만 쓴 판은 recall@5 가 1문항 안팎 오르내린다(0.05 에서 0.725 대 0.713, 0.3 에서 0.800 대 0.825, 측정 3). 한국어 글자 비중이 50% 이상인 청크 8개에서는 두 끝 원문 일치 비율이 0.838(57/68)로 오히려 높다(측정 14).
- 필터를 빼도 손실이 작다는 근거는 70B 결과 하나뿐이다. 작은 필터와 필터 없는 판을 견준 측정은 없다.
- 판정기로 gemma4 를 고르고 exaone 을 뺀 근거(측정 12), exaone 이 별칭을 지어내고 gemma4 가 다른 대상 이름을 별칭으로 낸 기록(`ASK/notes.md:886-887`, `ASK/lab/runs/22-eval.txt:4-12`).
- OpenIE 이름을 모든 청크 원문 선으로 걸면 새 문서 연결이 P 0.62 R 0.72 다(B1m, `ASK/lab/runs/13-eval.txt:62`).

무너진 주장:

- "포함 관계 차단이 오연결을 줄인다" 는 반박됐다. 판정 표본을 다시 세니 0.6~0.8 띠에서 포함 관계 쌍은 같은 대상 30/91, 다른 대상 9/91 이다. gemma4 가 맞힌 25쌍 중 14쌍, llama 가 맞힌 30쌍 중 12쌍이 포함 관계이고, 틀린 "예"(gemma4 2개, llama 5개)에는 포함 관계가 0개다(측정 12). 용어집 이름 [0.7, 0.9) 띠에서도 같은 대상 90쌍 중 45쌍, 다른 대상 102쌍 중 52쌍이 포함 관계다(측정 12). 이 규칙은 주로 맞는 쌍을 지운다.
- "그래프 판이 dense 를 이긴 적이 없다" 는 반박됐다. B1 0.850(`ASK/lab/runs/12-eval.txt:80`), 측정 4 의 0.863 이 있다. 맞는 말은 "흔들림 밖으로 이긴 적이 없다" 다.
- "작은 모델로는 jonex 탐색 루프가 먼저 무너진다" 는 근거가 없다. 우리 모델로 루프를 돌린 적이 없다.

치명적 결함(세 관점 모두): 포함 관계 차단을 판정 앞에 걸면 재현율이 (22 + 11)/221 ≈ 0.15 로 떨어져 공식 0.8 문턱(0.258)보다 나빠진다. 설계의 "R 약 0.21, 재현율은 그대로" 는 차단을 반영하지 않은 값이다. 판정 띠도 구성(0.7~0.9)과 기대치(0.6~0.8 측정)가 어긋난다. 내세운 "질의당 검색 LLM 0회" 는 dense A 도 같고, 이긴다고 적은 상대(공식 필터, JonexWiki 24회 루프)는 우리 기준선이 아니다. 동의어 정밀도가 올라도 그 선이 들어갈 PPR 순위는 dense 와 같거나 나쁘다(측정 3·4·5).

참고: 이 안은 승인 전의 gemma4 "예" 쌍을 잠정 선으로 그래프에 넣는다. 이것은 "애매한 것들은 로그로 두고 사람이 검토 후 다시 넣을 수 있는 형태" (`ASK/notes.md:19`)와 어긋난다.

## 조합안 검증이 다루지 않은 관점

### 답 생성 단계

권하는 조합의 답 단계는 dense 상위 5청크를 llama3.1:8b 에 한 번 넣는 것이다. HippoRAG 2 를 더해도 이 단계는 바뀌지 않는다. HippoRAG 2 는 passage 순위만 바꾸고, 트리플은 seed 고르기에만 쓰여 리더에 들어가지 않기 때문이다(논문 §3.5).

| 걸리는 곳 | 근거 | 이 조합에서의 처리 |
|---|---|---|
| 근거가 없을 때 거절 | "정보 부족" 이 정답인 질문에서 HippoRAG 2 85.71, RAG 96.01 이다(RAG vs. GraphRAG 표 2) | 그래프를 빼므로 RAG 보다 더 약해지는 몫은 들이지 않는다. 대신 "근거 없음" 답을 검토 로그로 세는 일은 따로 해야 한다 |
| 작은 리더가 엉뚱한 근거를 인용 | 정답 청크가 상위 5개에 든 질문은 38/40 인데 정답 근거를 인용한 답은 19/40 이고, 원문에 없는 인용이 하나라도 있는 답이 7/40, 인용이 없는 답이 1/40 이다(측정 13) | jonex 식 handle 복원은 "원문에 없는 인용" 을 없애지만 "엉뚱한 원문 인용" 은 막지 못한다. 실험 6단계가 잰다 |
| 답이 불완전할 때 | jonex 는 모르는 handle 이 남거나 인용이 하나도 없으면 답을 `incomplete` 로 표시한다(`JW/domain/engine/query/synthesis_orchestration.py:1098-1101`, `:446-448`) | 이 표시를 "애매한 것은 로그로" 의 입구로 쓴다 |

### 증분 갱신과 삭제

사내 위키는 보고서가 계속 들어오고 고쳐진다. 그래서 새 문서를 넣고 옛 문서를 지울 때 무엇을 다시 계산하는지가 비용과 정합을 정한다.

| 일 | 공식 HippoRAG 2 | JonexWiki | 권하는 조합 |
|---|---|---|---|
| 새 문서 넣기 | 같은 `save_dir` 로 `index()` 를 다시 부르면 없던 청크만 OpenIE·임베딩하고, 동의어 선은 새 phrase 와 전체 phrase 사이만 계산한다(`HR/HippoRAG.py:499-593`, `:1314-1317`). 문서를 하나씩 넣으면 동의어 계산 때문에 문서당 11초가 536번째에 1,104초로 늘었다는 보고가 있다(https://github.com/OSU-NLP-Group/HippoRAG/issues/170) | 이해 checkpoint 가 맞는 passage 는 LLM 을 다시 부르지 않는다(`JW/domain/engine/compile/understanding.py:399-459`) | 새 청크의 용어집 글자 매칭과, 새 이름 × 기존 항목의 대기열만 계산하면 된다. 이 증분 경로는 아직 짜지 않았다 |

| 사람 판정 기억 | 동의어 선은 색인 산출물이고 사람 판정 입구가 없다 | 동일성 판정을 저장하지 않고 compile 마다 다시 묻는다(`JW/domain/engine/compile/organization.py:441, 656`) | 제안: 판정 장부를 이름 쌍(정규화한 두 이름)을 키로 두어, 재색인이나 용어집 수정 뒤에도 "다름" 판정이 대기열에서 쌍을 계속 빼게 한다 |

## 권하는 실험 계획

### 무엇을 가르려는가

실험은 두 물음을 가른다. 첫째, 사람이 검토하는 이름 cosine 대기열이 "용어가 다른 쌍" 을 잇는가. 둘째, jonex 쓰기 규칙이 원문 추적을 실제로 낫게 하는가. 셋째로 PPR 을 다시 열지는 조건부 시험 하나로만 본다.

### 먼저 받아야 할 정답: 용어가 다른 쌍

지금 데이터에는 이 쌍이 0개다(측정 9). 그래서 정답을 먼저 만든다. 세 벌을 따로 보고하고 합치지 않는다.

| 정답 | 만드는 법 | 한계 |
|---|---|---|
| (가) 의미 기준 청크 쌍 | 회차 20 설계(`ASK/notes.md:815-829`)대로, 용어집과 옛 정답을 보지 않은 하위 에이전트가 새 5청크 × 옛 52청크 260쌍을 "의미가 같으면, 용어가 달라도" 기준으로 표시한다. 쌍마다 양쪽 표현을 원문 그대로 복사하고, 코드가 그 표현이 원문에 있는지 검사하고, 같은 용어인지 다른 용어인지 표시한다 | 다른 용어 쌍이 5개 미만이면 지표로 쓰지 않는다(`ASK/notes.md:823`). 정답과 용어집이 같은 Claude 계열이다 |
| (나) 바꿔 쓰기 사본 | 사용자와 다른 한 사람이 cosine 을 보지 않고 대치표를 쓴다. 연결 쪽은 새 5청크에서 옛 청크와 이어지는 대상 이름을 바꾼다. 새 5청크에 나오는 그런 이름은 AutoSchemaKG(#00·#01 에 한 번씩)와 앞선 실험 노트 이름(#02)뿐이고, squash merge 같은 다른 구조 대상은 새 5청크에 나오지 않는다(`ASK/lab/inputs/12-chunks.jsonl`). 구조 쪽은 구조 근거 68곳의 대상 이름 절반을 바꾼다. 둘 다 용어집에 없는 표현(한국어↔영어, 풀어 쓰기, 팀 내 약칭)으로 바꾼다. 예: AutoSchemaKG → "HKUST 자동 스키마 KG 도구". 바꾼 자리 표가 정답이다. 두 사람이 같은 대상을 따로 바꿔 두 벌을 만든다 | 바꾼 사람이 정답 대상을 안다. 한 사람의 어휘라 여러 작성자의 분포가 아니다. 연결 쪽은 바꿀 이름이 사실상 둘이라, 연결 정답 25쌍 중 22쌍의 성패가 AutoSchemaKG 이름 하나의 승인으로 정해진다. 그래서 연결 쪽은 쌍 재현율이 아니라 "바꾼 대상 가운데 대기열이 이은 대상 수" 로 센다. 바꿔 줄 다른 사람이 있는지 모른다 |
| (다) 실제 사내 보고서 표본 | 사용자가 줄 수 있으면, 같은 주제를 다룬 작성자 2명 이상의 보고서 20~50건에서 사람이 같은 대상 쌍을 표시한다 | 받을 수 있는지 모른다(#모르는 것과 물어야 할 것). 이 표본이 있어야 결론을 사내 용도로 옮길 수 있다 |

### 단계

| 단계 | 할 일 | 산출 |
|---|---|---|
| 0 | 고르는 값(대기열 문턱 0.65·0.7·0.75, passage 가중치, δ)을 실행 전에 파일로 적는다. 질문 40개를 홀수·짝수 두 겹으로 나누고, 값은 한 겹에서 골라 다른 겹에서 잰다 | 미리 정한 설정 파일 |
| 1 | 기준선을 다시 낸다. A 0.838·1000자 0.475(`ASK/lab/runs/21-eval.txt:19`), 글자 매칭 연결 P 0.44 R 1.00(`ASK/lab/runs/18-eval.txt:4`), 구조 0.58/0.63(`ASK/lab/runs/22-eval.txt:47`)이 같은 채점기로 나와야 한다 | 채점기 확인 |
| 2 | 항목 병합 대기열을 만든다. 항목마다 가장 가까운 항목 하나만 보낸다. 행마다 두 이름, cosine, 양쪽 이름이 나온 청크 id 와 원문 한 줄씩을 담는다. LLM 추출 이름은 원문에 글자 그대로 있는 것만 넣는다 | 대기열 파일 |
| 3 | 사람이 판정한다. 구조 정답을 보지 않은 검토자가 같음/다름/모름을 달고 쌍마다 시작·끝 시각을 남긴다. 같음은 별칭으로, 다름은 "다름 기록" 으로 남겨 다음 대기열에서 뺀다 | 판정 장부, 쌍당 시간 |
| 4 | 구조 질문을 다시 채점한다. 나누기 여섯(고정 1000·896·610, exaone·gemma4 주제 경계, 제목) × 판 다섯(기존 / 사람 승인 / 승인 + 조건부 fallback / 늘 합집합 / gemma4 자동 별칭). 정밀도는 맞힌 대상 평균과 빈 대상 수로 나눠 적는다 | 지표 (2) |
| 5 | 정답 (나) 사본에서 셋을 견준다: 글자 매칭만 / + 대기열 / + 대기열 + fallback. 후보 이름은 두 가지로 뽑는다. (i) llama3.1:8b 엔티티 단계 청크당 1회 + 원문 확인, (ii) LLM 없이 어절·영문 n-gram. 바뀐 대상마다 대기열 후보에 들었는지와 그 순위, 구조 재현율, 검토 수를 잰다 | 지표 (3)(6) |
| 6 | 답과 추적을 잰다. 리더는 llama3.1:8b 와 gemma4:e2b, temperature 0, num_ctx 8192 다. 판은 둘이다. B0 은 dense 상위 5청크에 청크 id 를 달고 인용을 자유 형식으로 받는다. B1 은 같은 청크를 코드가 문장으로 자르고 `[E1]`.. handle 을 달아, 모델은 handle 만 쓰고 코드가 문자 구간으로 되살린다. 모르는 handle 은 버리고 세며, 교정 턴은 두지 않는다(질의당 답 1회를 지키려고). 잴 것: 정답 `answer` 포함 일치율, 정답을 쓴 세션과 다른 판정자의 맞음/틀림, invalid handle 비율, 추적 정확도(인용 구간이 정답 근거 구간의 50% 이상을 덮는 답의 비율), "근거 없음" 비율 | 지표 (4) |

### 성공 기준과 중단 기준

- 구조: 정답을 보지 않은 검토자의 승인으로 나누기 여섯 모두에서 재현율이 기존 별칭 매칭(0.63~0.66)보다 0.15 이상 오른다. 맞힌 대상 정밀도는 0.05 넘게 떨어지지 않는다. 재현율이 gemma4 자동 별칭 판(0.79~0.84)보다 높다.
