# 네트워크 검증 말뭉치 검색 아키텍처 종합 보고서

작성 2026-10-13, team-lead. 9단계 절과 결론 7~8 은 2026-10-14 에 더했다. 근거는 판마다 `runs/23-arch-<이름>/` 의 `score.txt`·`detail.jsonl`·`REPORT.md` 와 진행 기록 `reports/net-arch-progress.md` 다. 숫자는 정답 v1(sha256 `29a02342…`)로 채점한 것만 견준다.

## 결론

1. 가장 큰 이득은 용어집이 아니라 단위였다. 문서에서 뽑은 주장(claim) 하나를 단위로 두고, 찾을 때만 문서 제목과 절 종류를 이름표로 붙이고, 돌려줄 때는 원문 구간을 주는 판(claim-ctx)이 고정 청크 dense 를 5000자 재현율 0.400 → 0.530 으로 올렸다(85승 29패). 질의 때 LLM 을 부르지 않는다.
2. 추상화 가운데 이긴 것은 값 개념 하나다. 질문의 연도·3GPP Release·소프트웨어 버전을 개념으로 읽어 claim 을 거르면 claim-ctx 대비 11승 2패(p=0.02)다. 사용자가 든 "2025·2026 → 연도" 가 이 경우다.
3. 범주 개념 펼치기("통신사 → SKT·KT·Verizon"), 용어집 노드 그래프 PPR, 용어집으로 후보 거르기, entry 이름으로 질문 넓히기는 claim-ctx 를 이기지 못했다. 거르기(20승 59패)와 질문 넓히기(8승 42패)는 크게 졌다. 원인은 판마다 이렇다. 펼친 갈래가 글자 예산을 먼저 가져가고, 집계 근거는 이름 대신 "16 vendors" 같은 요약 문장이다. 그래프 흐름은 차수 큰 제품 이름(Open5GS·free5GC)으로 쏠린다. 거르기는 답이 적힌 문장에 질문의 용어가 없을 때 근거를 버리고, 질문 넓히기는 붙인 이름이 질문 벡터를 묽게 만든다.
4. 질의를 칸으로 나누는 레코드 표(안 4, 질의마다 Haiku 1번)는 claim-ctx 와 갈리지 않지만 질문 종류마다 강약이 다르다. 개요·시간 유형에서 이기고(5000자 16승 5패, 15승 6패) 다중 홉에서 진다(9승 17패). 그래서 다음 판은 질문 종류에 따라 길을 고르는 라우터가 자연스럽다.
5. 용어집은 용어가 다른 대상·한국어 질문에서 조금 돕는 기미가 있다. 레코드 표 용어집 판 v2 에서 용어 다름 유형이 0.508 → 0.569, 한국어 질문이 메타 필터 판 대비 23승 9패(p=0.02)다. 대신 영어 질문에서 진다. 우연 이상으로 claim-ctx 를 넘은 용어집 판은 아직 없다. 사람 검토의 값도 아직 드러나지 않았다. Opus 가 검토한 용어집과 Haiku 후보를 그대로 쓴 용어집이 같은 구조에서 18승 23패(p=0.53)다.
6. 검색이 나으면 답도 낫다. 레코드 표 판의 답 정답성은 0.593~0.600 으로 고정 청크 0.455~0.457 보다 높고, 근거를 다 가져온 문항은 0.89~0.98 을 맞힌다. 답 문장마다 근거 번호 `[E#]` 를 달게 하면 정답성은 그대로지만 받치지 않는 인용이 0.3~3.5% 로 준다. 다만 답의 절반 넘게가 번호 빠진 문장을 가져서, 교정 턴이나 문단 단위 번호가 필요하다.
7. 용어집이 모델이 모르는 이름을 이을 때는 이겼다(9단계, #9단계: 모르는 용어 층과 구심점 카드). 공개 이름을 사내 이름으로 바꾸면 claim-ctx 재현율이 0.489 → 0.356 으로 떨어진다. 이 빈틈을 메운 것은 레코드 표 길에서 슬롯 값을 구심점 카드로 푸는 판 하나다. Haiku 슬롯 + 카드는 0.461 로 claim-ctx 를 56승 25패(p=0.00)로 이기고, 같은 판에서 카드만 빼면 0.353 으로 claim-ctx 와 비긴다(46승 11패로 카드 있는 쪽이 이김). 공개 이름 질문(0.491)과는 20승 22패로 갈리지 않는다. 그래서 결론 3·5 의 "용어집 판은 claim-ctx 를 넘지 못했다" 는 공개 이름 말뭉치에서만 맞는다. 모델이 이미 아는 이름이었기 때문이다.
8. 작은 모델(qwen3:8b)은 이 연결을 해내지 못했다. 슬롯을 qwen3:8b 가 채우면 같은 카드로도 0.309 로 무너진다(Haiku 대비 9승 50패). 카드를 답 프롬프트에 넣는 것(문맥 카드)은 답 정답성을 바꾸지 못했다(8승 8패, 맞는 카드로도 6승 4패). 정답은 문서 속 사실이고, 카드는 대상을 가리킬 뿐이기 때문이다. 카드는 검색의 일치 단계에서 일하고, 답 단계에서는 일하지 않는다.

claim-ctx 는 질의 때 LLM 을 부르지 않아서, 운영 모델 Qwen 32B 로 바꿔도 질의 쪽에서 달라지는 것은 없다. 색인 때 claim 을 뽑는 일은 Haiku 가 했다. 질의 때 LLM 을 쓰는 판(값 개념 필터, 레코드 표, 개념 펼치기, 답)과 claim 추출은 Haiku 와 Qwen 32B 의 차이를 재지 않아서 모른다. 같은 250문항을 Qwen 32B 로 한 번 돌리면 알 수 있다.

### 사용자가 든 방향마다

- jonex 처럼 주장을 뽑아 passage 로 임베딩: claim 단위만으로는 0.380 으로 고정 청크와 같다. 제목·절 종류 이름표를 붙이자 0.530 이 됐다. 주장 단위는 이름표와 함께일 때 일한다. 원문 발췌 대조에서 맞지 않은 claim 은 28,473 중 96개다.
- LinkedIn 처럼 issue 를 구조로 나눔: 이슈 구조 트리(증상·원인·재현·해결 칸)는 0.203 으로 졌다. 트리를 따라 내려가는 대신 절을 자유롭게 고르는 사후 판이 1000자에서 B0 를 이겼지만(55승 35패) 5000자에서는 0.368 이다. 칸 사이의 명시 선은 기여가 0 이었다. 의미 단위로 나누는 생각은 claim 단위가 더 잘 받았다.
- 용어집 중심 구조: 질문을 entry 에 잇는 일은 대체로 됐다. 하지만 entry 로 후보를 거르면 크게 지고(0.391), entry 를 이름표로만 붙이면 claim-ctx 와 같다(0.538). 그래프로 퍼뜨리면 제품 이름으로 쏠린다. 이 말뭉치에서 용어집은 "어디서 찾을지" 를 정하는 문지기로는 해롭고, 이름표나 보조 신호로는 해가 없다.
- 추상화 계층: 값 개념(연도·Release·버전)은 이겼고 범주 개념(통신사·벤더·NF)은 졌다. 범주를 펼친 61문항 중 29문항은 틀린 개념이었다(주제어 "크래시" 를 장애 유형 범주로 읽음 17 등). 개념이 맞은 32문항도 4승 12패다.
- 질문이 어떤 path 로 흘러 정답을 찾는지: 모든 판이 단위마다 path 를 남긴다(예 `glossary=AMF>abstraction=NF>unit=claim`). 레코드 표 판은 찾은 근거의 @5 64개가 표에서, 50개가 dense 채움에서 왔다. 섞기(채움)가 레코드 표 판 이득의 대부분(+0.120)이고 메타 필터가 +0.031 이다.

## 용어집 판 상세: 안 1 용어집 허브

자세한 것은 `runs/23-arch-a1-glossary/REPORT.md`(arch-glossary)다. claim-ctx 위에 용어집을 얹는 방식 셋과, 사람 검토 몫을 재는 판 하나를 돌렸다. 질문을 entry 에 잇는 일은 글자 매칭 + Haiku 1번이고, 250번에 실패 0, $0.333 이다.

| 판 | 용어집을 쓴 곳 | 5000자 | claim-ctx 대비 5000자 |
|---|---|---:|---|
| `a1-glossary` | 질문 entry 가 태그된 claim 만 후보로 거름 | 0.391 | 20승 59패 (p=0.00) |

| `a1-nocurate` | 위와 같되 Opus 검토 없는 용어집(Haiku 후보 5,609개 그대로) | 0.519 | 16승 23패 (p=0.34) |

- 거르기가 진 것은 답이 적힌 문장에 질문의 용어가 없을 때가 많아서다. claim-ctx 가 찾고 거르기 판이 놓친 근거 83개 중 72개는 근거 claim 에 질문 entry 가 없어 후보 밖이었다. 질문의 용어는 문서나 절에는 있지만 답이 적힌 문장에는 없을 때가 많다.
- 질의 확장은 질문당 이름이 중앙값 8개 붙어 질문의 증상·조건 낱말이 묽어졌다[추정](사례: 질문 글이 중앙값 1.26배로 늘고 한국어 질문이 영어 근거를 찾은 수도 164 → 136 으로 준 판, 1건). 한국어 질문을 영어 근거에 잇는 효과를 기대했지만 반대였다.
- 이름표 판만 한국어 질문이 영어 근거에 닿는 수를 늘렸다(5000자 164 → 182, 검정 안 함). 검토 없는 용어집 판에서는 163 으로 돌아갔다. [추정] 이 몫은 Opus 가 단 한국어 개념 이름과 한국어 별칭에서 온다(사례: 개념 줄이 없는 검토 없는 판이 claim-ctx 와 같아진 판, 1건).
- 사람 검토의 값은 이번 판들로는 드러나지 않는다. 검토한 용어집과 안 한 용어집이 이름표 구조에서 18승 23패(p=0.53)다. 검토 값이 거르기 같은 문지기 구조에서 크게 나타날 수는 있지만, 그 구조 자체가 claim-ctx 에 크게 져서 재지 않았다.

## 답 단계

자세한 것은 `runs/23-answer/REPORT.md`(arch-answer)다. 세 검색 판의 상위 5000자를 Haiku 에게 주고 답하게 한 뒤 Opus 가 0/0.5/1 로 채점했다. 두 형식을 견줬다. 자유 형식(free)과 답 문장마다 근거 번호 `[E#]` 를 다는 형식(eref)이다. eref 는 jonex 의 인용 규칙을 옮긴 것이다. 레코드 표 판에는 근거 번호가 빠진 문장을 짚어 한 번 더 고치게 하는 교정 턴 판(eref-fix)을 더했다.

- 검색이 나으면 답도 낫다. 근거를 다 가져온 문항의 정답성은 0.89~0.98, 하나도 못 가져온 문항은 0.17~0.24 다. 레코드 표 판은 B0 를 답에서도 55승 13패로 이기고, 이긴 55문항 중 48문항은 검색 재현율도 오른 문항이다. 그래서 이 말뭉치에서 답 품질의 병목은 답 모델보다 검색이다.
- 근거 번호는 정답성을 바꾸지 않지만 인용을 정직하게 만든다. 받치지 않는 인용이 8.5~15.1% 에서 0.3~3.5% 로 줄고, 근거 있는 문항의 거절도 준다. 번호가 가리키는 구간을 되살리지 못한 경우는 750답에서 0번이다.
- 대신 eref 답의 57~60% 가 번호 빠진 문장을 가진다. Haiku 가 번호를 문단 끝에 한 번만 다는 버릇 때문이다. 교정 턴 1회가 이 비율을 0.576 → 0.312 로 줄이지만, 다중 홉 정답성이 0.56 → 0.50 으로 내려간다. [추정] 교정 지시가 이어 주는 추론 문장을 지우거나 유보로 바꾼다(사례: 교정 뒤 진 8문항 중 다중 홉 5, 읽은 채점 메모 4개 중 유보 2). 그래서 운영에서는 문장 단위 대신 문단 단위로 번호를 요구하는 쪽을 먼저 재 볼 만하다.
- 근거 없음 29문항은 모든 판이 26~29개를 거절했다.
- 비용은 Haiku $4.57, Opus 채점 $93.84 다. 처음 실행의 1,191건 실패는 API 에 닿기 전에 막힌 것이었고 [추정] 사용량 한도로 본다(사례: 05:38~06:29 의 새 호출 전부가 실패하고 06:52 재시도가 모두 성공, 1번). 다시 돌린 뒤 실패는 0 이다.

## 9단계: 모르는 용어 층과 구심점 카드

### 왜 다시 쟀나

8단계까지의 용어집은 말뭉치에서 만든 공개 용어(Open5GS, KT 같은 이름)였다. 대리 모델 Haiku 와 임베딩 bge-m3 가 이미 아는 이름이라, 용어집이 모델에 새로 주는 것이 없었다. 그래서 9단계는 모델이 모르는 사내 이름을 만들어 같은 물음을 다시 쟀다. 사용자가 정의한 용어집 두 종류를 이렇게 옮겼다. 구심점 용어는 확정 사실을 박아 둔 카드이고, 관계 용어는 용어끼리 이을 수 있는 관계의 닫힌 목록이다. 목록 밖 관계로는 선을 만들지 않고 따로 셌다. 약속은 `reports/net-arch-stage9.md` 다.

### 빈틈

공개 이름 → 사내 이름에서 claim-ctx 의 5000자 재현율은 alias 151문항에서 0.489 → 0.356 이다(48승 15패, p=0.00). 사내 이름 판에서 한국어 질문(121개)은 0.299 로 영어 질문(30개) 0.585 보다 낮다. fact 묶음은 카드 없이도 0.750 이라 빈틈이 없다. 질문이 로그 문구와 수치를 함께 담고 있기 때문이다.

### 검색 판 (근거 있는 alias 151, 5000자)

- 레코드 표 길은 카드가 있을 때만 빈틈을 메운다. 카드 없는 Haiku 판은 슬롯 값에 사내 별칭이 들어가도 그 별칭을 쓴 문서의 레코드만 잡는다. 별칭이 문서마다 다르기 때문이다. 카드 표면이 든 슬롯 값 101개 가운데 99개가 그랬다(`runs/23-cf-table/REPORT.md`).
- 관계 선 그래프는 근거의 32.5% 에만 닿는다. 닿은 근거는 끌어올리지만(5000자 안 74묶음, claim-ctx 39), 질문마다 선 길 claim 이 중앙값 322개라 claim-ctx 가 찾던 근거를 밀어낸다. 그래서 5000자에서 비기고 2500자에서 진다(14승 31패, p=0.02). 선의 순위가 질문과 선 글의 cosine 하나뿐이라, 질문과 낱말이 겹치는 오류 메시지 선이 위를 차지한다(`runs/23-cf-relgraph/REPORT.md`).
- 질의 다시 쓰기는 작은 모델이 엉뚱한 카드를 고른 문항에서 그 이름을 질의에 넣어 검색을 흐렸다. 연결이 깨끗했던 21문항에서는 한 번도 지지 않았다(`runs/23-cf-answer/REPORT.md`).

### 작은 모델의 몫

- 연결: 작은 모델이 후보 카드 20장 가운데 고르면 정밀도 0.310, 재현율 0.426 이다(alias 159). 정답 카드는 후보 20장 안에 늘 있었다. 글자 매칭은 정밀도 1.000, 재현율 0.987 이다. 다만 alias 질문은 이름 바꾸기에서 코드로 만들었기 때문에, 글자 매칭이 맞는 것은 당연하다. 실제 사내 질문에서 별칭이 얼마나 정확히 적히는지는 모른다.
- 슬롯: 같은 카드로 qwen3:8b 는 0행 문항이 66%, Haiku 는 26% 다. qwen 은 필터를 많이 걸고(중앙 4개), 값을 틀린 칸에 넣고(AMF 를 제조사 칸에), 서술 낱말을 값으로 쓴다.

## 용어집 관리 비용

용어집이 성능 이점을 주려면 사람이 관리하는 일이 따른다. 이번에 Opus 가 대신한 관리에서 다음이 드러났다.

- 정규화 키가 겹치는 쌍 696개(개념 노드 119·entry 461 이 얽힘). 개념 노드 별칭에 entry 이름이 580번 들어가서 레코드 표 v1 과 개념 펼치기가 졌다. 저장 전에 별칭이 다른 항목의 정식 이름인지 검사하는 규칙이 필요하다(`inputs/net-corpus/glossary/CURATION.md`).
- 검색이 빈자리를 드러냈다. 노드가 없는 범주 다섯 개(중국 벤더, 클라우드 사업자, MPLS Forum·EANTC 시험, 장애 유형 노드의 주제어 문제, "Code Orange" → Orange 오매칭)를 `review-queue.jsonl` 에 올렸다. 그래서 고리가 둘 필요하다. 저장 전 충돌 검사와, 검색 실패에서 대기열로 가는 고리다.
- 표본에서 일반어 별칭(`BGP session` ← `Peer`, 129문서), 남은 같은 대상(`guti`·`5g-guti`), 틀린 부모를 봤다.
- 비용: 용어집 구축 Opus $21.98 + Haiku $4.89, 레코드 칸 정규화 Opus $3.54.

## 다음에 권하는 방향

운영 모델 Qwen 32B 로 레코드 표 슬롯을 한 번 채워 보는 것을 먼저 권한다. 9단계에서 사내 이름의 빈틈을 메운 길은 "레코드 표 + 구심점 카드" 하나다. 그 길은 슬롯 모델이 Haiku 면 서고, qwen3:8b 면 무너진다. 그래서 Qwen 32B 가 어느 쪽인지가 이 아키텍처를 쓸지 정한다. 같은 199문항, 같은 프롬프트, 같은 카드로 슬롯만 바꾸면 되고, 질의 LLM 은 슬롯 한 번뿐이다.

- Qwen 32B 가 Haiku 쪽이면: 용어집을 구심점 카드(사실을 박은 사내 용어)로 관리하고, 레코드 표의 칸 값을 카드로 푸는 길을 바탕으로 둔다. 관리할 것은 카드의 별칭 목록이다. 이번 결과에서 이긴 몫은 카드의 별칭 표면이 만들었다. 박아 둔 사실이 검색을 도운 증거는 아직 없다.
- Qwen 32B 도 qwen3:8b 쪽이면: 슬롯 프롬프트를 좁힌다(필터 상한, 칸마다 예시 값). 또는 슬롯 대신 글자 매칭으로 질문의 사내 별칭을 카드에 잇고, 그 구심점의 레코드만 거르는 길을 잰다. 9단계 연결에서 글자 매칭은 작은 모델 고르기보다 정확했다.

8단계에서 권한 질문 종류 라우터는 그 뒤로 미룬다. 8단계 판들의 유형별 강약은 공개 이름 말뭉치에서 잰 것이라, 사내 이름에서 다시 재야 한다. 답 단계에서는 카드를 넣기보다 근거를 짧게 주는 쪽을 먼저 재 볼 만하다. 근거 없는 질문 거절은 Qwen 32B 에서 따로 재야 할 첫 항목이다.
