# 용어집 중심 검색·링크 아키텍처는 구조가 다른 여덟 안으로 나뉘고, 질문 유형 일곱 가지가 그 안들을 가른다. 외부 근거가 가장 뚜렷한 곳은 이슈 구조 트리(단일 사실·다중 홉), 필드 레코드 표(집계), 개념 계층 펼치기(범주 모으기)이고, 용어집 허브 자체의 효과는 아직 어느 출처도 따로 재지 않았다

작성 2026-10-13. 이 글은 네트워크 검증 부서 말뭉치(이슈 스레드, 시험·상호운용 보고서, 한국어 글) 실험의 3단계 산출이다(`ASK/lab/reports/net-arch-progress.md` 의 단계 표). 목적은 파라미터 조정이 아니라 구조가 서로 다른 안을 고르는 재료를 모으는 것이다.

## 판정 요약

- 단위·연결·질의 경로 부품을 #부품 에 출처 숫자와 함께 모았다. 부품은 단위 다섯, 연결 다섯, 질의 경로 여덟이다.
- 조합안은 여덟이다. 질문이 처음 닿는 곳(용어집 entry, 개념, 문서 섹션, 레코드 표, 그래프, 요약 페이지, 라우터, 에이전트)이 안마다 달라서 path 의 첫 단계 종류로 갈린다.
- 외부 근거로 가장 뚜렷한 이득은 셋이다. LinkedIn 의 이슈 트리 + 이슈 간 그래프는 평문 임베딩 대비 MRR 을 0.522 에서 0.927 로 올렸다(2404.17723 표 1). 레코드 표 + SQL 은 집계 질문에서 벡터 RAG 0.331 을 0.518(추론 schema)·0.899(정답 schema)로 올렸다(S-RAG 2511.08505 표 3). 조직 계층 트리는 "범주 아래 엔티티 나열" 질문을 45.5% 에서 68.2% 로 올렸다(T-RAG 2402.07483 표 4).
- 용어집 하나만 넣고 뺀 검색 ablation 은 찾지 못했다. 가장 가까운 Telco-RAG 의 84.8% → 90.8% 는 청크 크기·router·질의 보강이 함께 바뀐 값이다(2404.15939 표 I·II). 그래서 "사람 용어집이 큰 성능 이점을 준다" 는 이 실험이 처음 재는 가설이다.
- 질문 유형은 일곱이다. 요청받은 다섯(단일 사실, 다중 홉, 모으기·집계, 용어가 다른 같은 대상, 연도·기간 조건)에 개요·전역 질문과 근거 없음 질문을 더했다. 앞의 것은 요약 페이지 안을, 뒤의 것은 fallback 동작을 가른다.

| 에이전트 탐색 | LLM 이 여러 턴 동안 도구를 골라 하위 질문을 푼다 | RouteRAG-7B 는 평균 EM 51.9 로 vanilla RAG 19.0 을 넘었지만, RL 학습을 빼면 3B 판이 47.0 에서 24.0 으로 떨어졌다(2512.09487 표 1·2). KAG 의 logical form 은 질의당 89,746~110,532 토큰, 46~58초가 든다고 HiRAG 가 쟀다(2503.10150 표 3) | 학습 없는 작은 모델 루프의 근거가 약하다 |
| 구조화 질의·필터 | 질문을 표 질의나 시간 필터로 바꾼다 | GlobalQA 에서 일반 RAG 의 count F1 은 0.93 이다(2510.26205 표 2, Qwen2.5-14B). TAG 의 집계 제외 60문항에서 RAG 0.00, Text2SQL 0.17, 손으로 짠 TAG 0.55 다(2408.14717 표 1). TempRALM 은 질의 시점보다 뒤의 문서를 빼고 시간 점수를 더해 EM 을 41.72 에서 72.65 로 올렸다(2401.13222 표 1) | 질의 생성이 틀리면 조용히 빈 결과가 된다. S-RAG 는 추론 schema 가 단위를 못 맞춰 1M·1B 가 둘 다 "1" 이 된 사례를 적었다 |

## 조합안

### 기준선

조합안과 견줄 기준선은 둘이다. B0 은 bge-m3 dense 고정 청크(path `dense`), B1 은 2단계에서 만든 공식 HippoRAG 2 + Haiku 사본이다(path `ppr:phrase=...`, `ASK/lab/runs/23-hr2-README.md`). 기준선은 조합안 개수에 넣지 않는다.

### 여덟 안 한눈에

| 안 | 이름 | 질문이 처음 닿는 곳 | path 첫 단계 | 색인 Haiku 호출 | 질의 Haiku 호출 | Opus 검토 자리 |
|---|---|---|---|---|---|---|
| 1 | 용어집 허브 + claim | 용어집 entry | `glossary` | 청크당 1~2 (claim) | 링크 1 + 답 1 | 별칭 승인 대기열, 미등록 용어 로그 |
| 2 | 개념 계층 펼치기 | 개념 | `abstraction` | 안 1 과 같음 | 파싱 1 + 답 1 | 개념 트리 소속 |
| 3 | 이슈 구조 트리 + 문서 간 그래프 | 문서 섹션 | `section` | 문서당 1 (섹션 경계) | 파싱 1 + 답 1 | YAML 템플릿, 파싱 실패 표본 |
| 4 | 필드 레코드 표 + 구조화 질의 | 레코드 표 | `table` | 문서당 1~2 (레코드) | 슬롯 1 + 답 1 | 표 칸(schema), 정규화 실패 값 |

| 6 | 항목 페이지 계층 | 요약 페이지 | `page` | 안 1 + entry·개념마다 페이지 1 | 답 1 | 페이지 인용 표본 |

모든 안은 결과가 비면 dense 로 되돌아가고 그 단위의 path 를 `fallback=dense` 로 적는다. 그래서 채점기가 "그 안의 경로가 실제로 답을 찾았나" 와 "fallback 이 찾았나" 를 따로 센다.

### 1. 용어집 허브 + claim

색인은 세 단계다. Haiku 가 청크마다 원문 그대로의 claim 발췌를 내고, 코드가 공백만 정규화한 부분 문자열 검사로 발췌를 확인해 문자 구간을 고정한다(jonex 규칙, `JW/domain/engine/compile/understanding.py:576-584` 를 `ASK/lab/reports/hipporag2-jonex.md` 가 인용).

코드가 claim 마다 용어집 정식 이름·별칭이 글자로 든 entry 를 태그한다. claim 과 원래 청크를 모두 bge-m3 로 임베딩한다.

질문이 흐르는 path:

1. 코드가 질문에서 용어집 글자 매칭을 하고, Haiku 가 한 번 더 용어집 후보 목록을 보고 질문 속 용어를 entry 에 연결한다. 목록에 없는 용어는 "미등록" 로그로 보낸다(Golden-Retriever 2408.00798 §3.2 는 문자열 일치가 오타·미등록 용어를 놓쳐 LLM 으로 뽑았다).
2. 연결된 entry 가 태그된 claim 만 후보로 남긴다.
3. 후보 안에서 bge-m3 순위를 매긴다.
4. 상위 claim 의 원문 구간에 그 claim 이 든 청크를 부모로 붙여 돌려준다(small-to-big).
5. entry 가 0개면 dense 로 간다.

path 예: `glossary=PFCP>unit=claim`, `glossary=UPF>unit=claim>parent=chunk`.

강할 질문은 용어가 다른 같은 대상과 단일 사실이다. 용어가 다른 대상은 별칭이 용어집에 있는 한 글자 매칭이 잇기 때문이다. 우리 기록에서 사람 승인 병합 3쌍을 넣으면 구조 질문 재현율이 0.63 에서 0.86~0.90 으로 올랐다(측정 11, 다만 정답을 보고 고른 병합이다). Dense X 의 드문 엔티티 이득(2312.06648 §5.2)도 claim 단위 쪽 근거다.

약할 질문은 다중 홉과 집계다. 두 entry 를 잇는 경로가 없고, 상위 k 에서 잘리기 때문이다. 용어집 밖의 새 용어도 dense 로만 간다.

Opus 는 별칭 승인 대기열을 본다. 대기열은 bge-m3 이름 cosine 이 미리 정한 문턱 이상인 이름 쌍이다. 57청크에서 문턱 0.7 이면 승인 1건마다 약 20쌍을 봐야 했다(측정 11).

### 2. 개념 계층 펼치기

색인은 안 1 위에 개념 트리를 더한다. Opus 가 entry 마다 상위 개념(예: `통신사`, `벤더`, `5G NF`, `프로토콜`)을 정한다. `연도` 는 코드가 문서 날짜와 본문 연도 정규식으로 claim 에 붙인다.

질문이 흐르는 path:

1. Haiku 가 질문에서 개념("통신사별"), instance("SKT"), 조건("2024년 이후")을 뽑는다.
2. 개념이면 코드가 트리에서 하위 instance 를 모두 펼친다.
3. instance 마다 안 1 의 2~4단계를 따로 돌려 instance 별 상위 m 개를 얻는다.
4. 연도 조건이 있으면 claim 의 연도 태그로 거른다.
5. 결과를 instance 별로 묶어 답 모델에 넘긴다.

path 예: `abstraction=통신사>glossary=SKT>unit=claim`, `abstraction=연도:2024-2026>glossary=SRv6>unit=claim`.

강할 질문은 모으기("통신사별 ~ 이슈")와 연도·기간 조건이다. T-RAG 는 범주 아래 엔티티를 묻는 complex 질문에서 트리를 넣어 45.5% 를 68.2% 로, 다른 조직 데이터에서 46.2% 를 61.5% 로 올렸다(2402.07483 표 4, §6.2.1). 문항이 22개, 13개로 작다.

기간 조건은 TimeR4 에서 질문의 시간 표현을 명시 날짜로 다시 쓰는 단계를 빼면 Hits@1 이 72.8 에서 61.12 로 떨어졌다(EMNLP 2024 표 5).

약할 질문은 개념 이름이 질문에 없는 경우다. [추정] "이동통신 3사" 처럼 트리에 없는 말로 범주를 부르면 1단계가 개념을 못 찾는다(사례: T-RAG 는 이름이 매칭될 때만 트리를 쓴다, 1건).

Opus 는 새 instance 의 개념 소속 대기열을 본다. 트리에서 instance 가 빠지면 집계 답에서 조용히 빠지므로 이 검토가 이 안의 정확도를 정한다(#위험).

### 3. 이슈 구조 트리 + 문서 간 그래프

색인은 문서 종류별 YAML 템플릿에서 시작한다. Opus 가 템플릿을 정한다. 예를 들어 이슈는 제목·증상·환경(장비·버전·통신사)·재현·원인·해결·댓글 메시지, 상호운용 보고서는 시험 항목·참여 벤더·구성·결과·관찰이다.

GitHub 이슈 필드나 보고서 표 제목처럼 규칙으로 되는 곳은 코드가 자르고, 나머지는 Haiku 가 템플릿을 보고 섹션 경계만 지목한다. 원문을 다시 쓰게 하지 않는 것은 MoC 와 Chroma 가 조각을 다시 쓰면 원문이 바뀐다고 적었기 때문이다(`chunking-criteria.md` 방법 9).

문서 간 선은 셋이다. 명시 선은 이슈 번호·URL·"see also" 참조다. 암묵 선은 제목 임베딩 cosine 이 미리 정한 θ 이상인 쌍이다(LinkedIn 2404.17723 §3.1). 용어집 선은 같은 entry 를 공유한 쌍에 Adamic-Adar 점수를 단 것이다(회차 18).

질문이 흐르는 path:

1. Haiku 가 질문을 "섹션→값" 조각과 intent(원인을 묻나, 해결을 묻나)로 나눈다.
2. 조각마다 같은 섹션 노드와만 cosine 을 구해 문서별로 합치고 상위 K 문서를 고른다.
3. 코드가 고른 문서의 intent 섹션과, 명시 선 1홉 이웃의 같은 섹션을 꺼낸다. LinkedIn 은 이 자리에서 LLM 이 Cypher 를 만들지만, 이 안은 코드 고정 질의로 둔다. Golden-Retriever 도 LLM 이 SQL 을 만들지 않고 템플릿으로 조회한다(2408.00798 §3.4).
4. 1단계 파싱이 실패하거나 2단계가 비면 dense 로 간다(LinkedIn 의 fallback 과 같은 자리).

path 예: `section=원인>doc=open5gs#1234>section=해결`, `section=증상>doc=eantc-2024>link=explicit>section=결과`.

강할 질문은 단일 사실(이 이슈의 원인·해결)과 링크를 따라가는 다중 홉이다. LinkedIn 은 같은 GPT-4·E5 조건에서 평문 임베딩 대비 MRR 0.522→0.927, Recall@1 0.400→0.860 을 냈고, 배포 뒤 해결 시간 중앙값이 7시간에서 5시간(28.6%)으로 줄었다(2404.17723 표 1·3). 평가 질문 수는 원문에 없다. CREST 는 기준별 조각을 하나라도 빼면 모든 지표가 떨어졌다(2511.17417 표 8).

약할 질문은 형식 없는 한국어 블로그 글에 대한 질문이다. CREST 에서도 기준을 모두 갖춘 보고서는 약 60% 였다(2511.17417 §4.1). 용어가 다른 같은 대상도 이 안에는 장치가 없다.

Opus 는 템플릿을 정하고, 파싱이 실패한 문서 표본을 보고 템플릿을 고친다.

### 4. 필드 레코드 표 + 구조화 질의

색인은 표 칸(schema)에서 시작한다. Opus 가 용어집 개념을 칸으로 삼아 칸을 정한다. 예: 문서, 시험 항목, 통신사, 벤더, 장비, 기능(entry), 연도, 결과(통과·실패·부분), 이슈 유형.

Haiku 가 문서마다 레코드 목록을 뽑되 칸마다 원문 발췌를 함께 낸다. 코드가 발췌를 원문에서 확인하고, 값이 용어집 entry 나 개념 instance 로 정규화되는지 검사한다. 정규화되지 않는 값은 Opus 대기열로 보낸다. 표는 SQLite 에 둔다.

질문이 흐르는 path:

1. Haiku 가 질문을 고정 질의 템플릿(필터, 묶기, 세기, 나열)의 슬롯으로 채운다. 슬롯 값은 entry 나 개념만 허용하고 자유 SQL 은 쓰지 않는다.
2. 코드가 질의를 실행한다.
3. 결과 행과 각 칸의 원문 구간을 근거로 돌려준다.
4. 슬롯을 못 채우거나 결과가 0행이면 dense 로 간다.

path 예: `table=records>filter=연도:2024>group=통신사`, `table=records>filter=기능:EVPN>count`.

강할 질문은 집계, "모두" 나열, 연도 조건이다. S-RAG 는 호텔 데이터 집계에서 벡터 RAG 0.331, 추론 schema 0.518, 정답 schema 0.899 를 냈다(2511.08505 표 3). 사람이 정한 schema 가 크게 앞선다는 점이 이 안에 Opus 를 두는 근거다.

GlobalQA 의 일반 RAG count F1 0.93(2510.26205 표 2)과 CRAG 의 "lower truthfulness for queries requiring aggregation"(2406.04744 §5.2)은 벡터 검색만으로는 이 유형이 무너진다는 쪽 근거다.

약할 질문은 원인·과정을 묻는 서술형과 schema 밖 정보다. 레코드 추출이 빠뜨린 것은 답에서도 빠진다. S-RAG 원문도 "limited to corpora that can be represented by a single schema" 라고 적었다(§8). 이슈·보고서·블로그가 섞인 우리 말뭉치에서는 문서 종류마다 표가 따로 필요할 수 있다.

Opus 는 칸을 정하고, 정규화되지 않은 값을 entry 로 붙이거나 새 entry 로 만든다.

### 5. 용어집 노드 PPR

색인은 안 1 의 claim·entry 태그를 그래프로 바꾼다. 노드는 entry, claim, 청크다. 선은 claim–entry(언급), entry–상위 개념(belongTo), claim–청크(포함), 문서 간 명시 선이다. OpenIE 트리플 대신 용어집 매칭으로 노드를 만들어 추출 호출이 안 1 과 같다. 측정 15 의 "LLM 없는 용어집 노드 PPR" 을 claim 층까지 넓힌 판이다.

질문이 흐르는 path:

1. 안 1 의 1단계로 질문 entry 를 연결한다.
2. 연결된 entry 를 PPR 시작점으로 두고, 청크는 dense 점수에 미리 정한 배율을 곱해 시작점에 더한다.
3. PPR 을 돌려 청크·claim 점수로 순위를 매긴다.
4. entry 가 0개면 dense 로 간다.

path 예: `ppr:glossary=PFCP|UPF>unit=claim`.

강할 질문은 두 대상 사이를 잇는 다중 홉이다. HippoRAG 2 는 2Wiki recall@5 를 76.5 에서 90.4 로 올렸다(2502.14802 표 3).

우리 쪽에서는 공식 HippoRAG 2 + Haiku 가 57청크에서 dense 와 4승 3패·3승 2패였고(진행 기록 1판·roles 판, 두 판 모두 이긴 문항은 s17 하나), 원래 설정 재구현은 dense 보다 낮았다(측정 3·4). 그래서 이 안은 "용어집 노드가 OpenIE 이름보다 나은 시작점인가" 를 B1 과 견주는 자리다.

약할 질문은 근거 없음 질문과 흔한 entry 를 거치는 질문이다. "정보 부족" 이 정답인 질문에서 HippoRAG 2 는 85.71, RAG 는 96.01 이었다(RAG vs. GraphRAG 2502.11371 표 2). 범용어 하나가 PPR 경로를 독점한 사례도 우리 기록에 있다(측정 10 의 `세션`).

Opus 는 흔한 entry 목록을 정한다. 이 목록의 entry 는 PPR 시작점과 선에서 뺀다(Block Purging 계열, `ASK/lab/reports/19-tentative-links.md` #1.4).

### 6. 항목 페이지 계층

색인은 안 1 의 claim 위에 요약 페이지 두 층을 쓴다. Haiku 가 entry 마다 태그된 claim 을 모아 항목 페이지를 쓰고, 개념마다 하위 항목 페이지를 모아 개념 페이지를 쓴다. 페이지 문장마다 `[E#]` 로 claim 을 인용하게 하고, 코드가 handle 을 claim 구간으로 되살리며 인용 없는 문장은 버린다(jonex `[E#]` 복원, `hipporag2-jonex.md` #JonexWiki 엔진의 요지).

계층은 LLM 군집이 아니라 안 2 의 사람 개념 트리를 그대로 쓴다. 이 점이 HiRAG·ArchRAG 와 다르다.

질문이 흐르는 path:

1. 개념 페이지 층에서 bge-m3 로 상위 k 개를 고른다.
2. 고른 개념 아래 항목 페이지에서 상위 k 개를 고른다(ArchRAG 2502.09891 의 top-down 처럼 위층 결과가 아래층 시작점이 된다).
3. 고른 항목 페이지가 인용한 claim 의 원문 구간을 꺼낸다.
4. 답 모델은 페이지 요약과 claim 원문을 함께 받는다.
5. 페이지 층이 비면 dense 로 간다.

path 예: `page=concept:통신사>page=entry:SKT>unit=claim`.

강할 질문은 개요·전역 질문("5G 코어 구축 글들이 공통으로 겪은 문제")이다. GraphRAG 는 가장 위층 C0 요약만 써도 벡터 RAG 대비 comprehensiveness 승률 72% 를 내면서 원문 map-reduce 보다 토큰을 97% 넘게 덜 썼다(2404.16130 표 2, 그림 2). 이 승률은 LLM judge 값이다.

약할 질문은 세부 단일 사실이다. 요약이 세부를 잃고, RAPTOR 이야기 2 에서는 세 층을 다 쓴 판이 맨 아래 층만 쓴 판보다 낮았다(2401.18059 표 14). 요약 환각은 RAPTOR 에서 4% 였다(부록 E). 새 claim 이 들어오면 그 entry 와 개념의 페이지를 다시 써야 하므로 갱신 비용도 가장 크다.

Opus 는 페이지 표본을 보고, 인용한 claim 이 그 문장을 실제로 받치는지 판정한다.

### 7. 질문 유형 라우터

색인은 안 1·3·4·6 의 색인을 모두 만든다. 여덟 안 중 색인이 가장 비싸다.

질문이 흐르는 path:

1. Haiku 가 few-shot 예시를 보고 질문 유형(#질문 유형 설계 의 일곱 가지)과 슬롯을 낸다.
2. 코드가 유형별 경로 표로 보낸다. 단일 사실은 안 3(이슈·보고서 문서면) 또는 안 1, 다중 홉은 안 3, 집계는 안 4, 용어가 다른 대상은 안 1, 연도 조건은 안 2 또는 안 4 의 필터, 개요는 안 6 이다. 근거 없음 유형은 따로 경로를 두지 않고 안 1 로 보낸다.
3. 경로가 비면 dense 로 간다.

path 예: `router=aggregation>table=records>group=통신사`, `router=single>section=원인>doc=free5gc#88`.

이 안은 "유형마다 다른 경로를 쓰는 것" 이 "가장 좋은 단일 안" 을 넘는지를 잰다. StructRAG 는 router 로 고른 판이 60.38, chunk 하나로 고정한 판이 53.92, 무작위 router 판이 45.33 이었다(2410.08815 표 3). router 정확도가 낮으면 이득이 사라진다는 뜻이다.

Haiku few-shot 의 router 정확도는 아무도 재지 않았고, 가장 가까운 숫자는 Qwen2-7B few-shot 66.12, Qwen2-72B few-shot 90.06 이다(그림 4).

약할 질문은 유형이 섞인 질문("2024년 이후 통신사별로 PFCP 실패 원인")이다. Adaptive-RAG 의 분류기는 다단계가 필요한 질문의 약 31% 를 단일 단계로 잘못 보냈다(2403.14403 그림 3).

Opus 는 라우터가 고른 유형과 정답 유형이 다른 질문 표본을 보고 few-shot 예시를 고친다. 정답 유형은 5단계 정답에 함께 적는다.

### 8. 도구 탐색 에이전트

색인은 안 7 과 같다.

질문이 흐르는 path:

1. Haiku 가 도구 여섯(용어집 찾기, 개념 펼치기, claim 검색, 레코드 질의, 이슈 하위 그래프, 원문 읽기) 가운데 하나를 골라 하위 질문을 푼다.
2. 도구 호출은 최대 8회로 미리 정한다.
3. 답에는 읽은 근거만 `[E#]` 로 인용하게 하고, 모르는 handle 이 남으면 답을 `incomplete` 로 표시한다(jonex `synthesis_orchestration.py:1098-1101` 을 `hipporag2-jonex.md` 가 인용).
4. 상한에 닿아도 읽은 근거가 0이면 dense 로 간다.

path 는 도구 호출 순서를 그대로 적는다. 예: `agent=glossary:PFCP>agent=section:원인>agent=read:open5gs#1234`.

강할 질문은 다중 홉과 유형이 섞인 질문이다. KAG 의 logical form 판은 2Wiki F1 76.2 로 IRCoT+HippoRAG 57.1 을 넘었다(2409.13731 표 8). RouteRAG-7B 는 여러 턴에서 passage·graph 검색을 골라 평균 EM 51.9 를 냈다(2512.09487 표 1).

약할 근거도 같은 출처에 있다. RouteRAG 3B 는 RL 학습을 빼면 평균 EM 이 47.0 에서 24.0 으로 떨어졌다(표 2). 이 안은 학습 없이 Haiku 를 쓰므로 그 아래쪽 숫자에 가까울 수 있다. KAG 는 "누가 나이가 많은가" 를 사망 시 나이 비교로 잘못 분해한 사례를 적었다(§6). 질의당 비용과 지연도 가장 크다.

Opus 는 `incomplete` 로 표시된 답과 도구 상한에 닿은 질문을 본다.

### 원칙

질문은 5단계에서 Opus 하위 에이전트가 말뭉치를 읽고 쓴다. 아래 예시는 틀이고, 실제 질문의 사실은 말뭉치에서 근거 구간을 복사할 수 있을 때만 쓴다. 말뭉치는 지금 수집 중이고 한국어 글(5G 코어 구축, BGP, MTU, O-RAN)과 EANTC·ETSI·IETF·O-RAN 상호운용 보고서가 들어오고 있다(`ASK/lab/inputs/net-corpus/raw/` 의 디렉토리 이름으로 확인).

검색 질문과 따로 문서 간 연결 쌍을 둔다. 쌍마다 "용어 같음" 과 "용어 다름" 을 표시하고, 다름 쌍이 5개 미만이면 지표로 쓰지 않는다는 회차 20 의 규칙(`ASK/notes.md:823`)을 그대로 둔다. 안 1·3·5 는 이 정답으로 링크 정밀도·재현율도 잰다.

| 경로가 빈 결과를 낸다 | LinkedIn 은 질의 실행에 문제가 생기면 평문 검색으로 되돌아간다(2404.17723 §3.2.3). 공식 HippoRAG 2 는 필터가 비면 dense 로 가고, 57청크에서 5/40 이 그랬다(진행 기록) | 모든 안이 dense 로 되돌아가고 path 를 `fallback=dense` 로 남긴다. 안마다 fallback 비율을 보고한다 |
| fallback 이 조용하다 | 공식 HippoRAG 2 는 필터 호출 예외를 빈 목록으로 바꿔 모든 질의가 조용히 dense 로 갈 수 있다(`hipporag2-jonex.md` #공식 코드의 결함) | fallback 마다 이유(파싱 실패, entry 0개, 0행, 상한)를 로그에 남긴다 |
| fallback 이 LLM 기억으로 간다 | Think-on-Graph 는 탐색이 깊이 상한에 닿으면 "generates the answer exclusively based on the inherent knowledge in the LLM" 한다(2307.07697 §2.1.3) | 이 실험의 fallback 은 검색만 한다. 근거 없이 답하는 경로를 두지 않는다 |
| 라우터가 틀린 경로로 보낸다 | Adaptive-RAG 는 fallback 이 없고, 분류기가 검색이 필요 없는 질문의 약 47% 를 한 번 검색 경로로 보냈다(2403.14403 그림 3). Semantic Router 는 문턱을 넘는 route 가 없으면 None 을 돌려준다(공식 저장소) | 안 7 은 라우터 결과가 비면 dense 로, 유형 확신이 낮으면 둘째 유형 경로도 돌린다 |
| 근거 없음 질문에 그래프가 약하다 | HippoRAG 2 는 "정보 부족" 이 정답인 질문에서 85.71, RAG 는 96.01 이었다(2502.11371 표 2) | 근거 없음 유형을 질문 세트에 넣어 안마다 거절률을 잰다 |
