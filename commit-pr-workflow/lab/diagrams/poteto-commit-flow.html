poteto 커밋 흐름도

브랜치에서는 커밋을 아끼지 않는데 main 에는 왜 PR 하나에 커밋 하나만 남는가. poteto 가 자기 에이전트에게 적어 둔 규칙 다섯 대목을 그림으로 옮겼다. 영어는 파일 원문, 한글은 번역.

브랜치 한 바퀴: 아낌없이 커밋하고, rebase 로 다시 짜고, squash 로 얹는다

Commit liberally. Rebase into small, ordered commits before opening PRs. Each commit is a future PR: landable, ordered to tell the story. 커밋은 아낌없이 한다. PR 을 열기 전에 rebase 해서 작고 순서가 있는 커밋들로 다시 짠다. 커밋 하나하나가 나중에 PR 하나가 될 수 있는 것이다. 혼자 올려도 되고, 이야기가 읽히는 순서로 놓여 있다. The squash commit body is the PR body. squash 커밋의 본문이 곧 PR 본문이다. playbooks/opening-a-pr.md 7번·13번 줄

실제 PR #366 이 이 모양이다. 브랜치에는 넷이 있었고 main 에는 하나가 남았다.

브랜치 (PR #366)                                     main
b9ae5c6 feat(pstack): setup-pstack budget ask        5bf2b15 feat(pstack): setup-pstack budget ask (#366)
c7fc5d3 docs(pstack): mention the budget in README     * feat(pstack): setup-pstack budget ask
5a453d3 refactor(pstack): tighten step 3               * docs(pstack): mention the budget in README
ce30f2c fix(pstack): step 3 rebuilds before the budget * refactor(pstack): tighten step 3
                                                       * fix(pstack): step 3 rebuilds before the budget

고침이 생기면: amend 인가, 새 커밋인가

Amend when the fix belongs in a just-made commit. New commit when separable. 고친 내용이 방금 만든 커밋에 속하면 amend 로 그 커밋에 넣는다. 떼어낼 수 있는 것이면 새 커밋으로 만든다. playbooks/opening-a-pr.md 7번 줄

플레이북마다 커밋의 순서가 정해져 있다

Stage the commits so the failing repro lands before the fix in git history. 실패를 재현하는 커밋이 고치는 커밋보다 먼저 git 기록에 들어가도록 커밋을 배치한다. A subtraction commit, then the reshape, then any follow-on cleanup. 먼저 빼는 커밋, 그다음 모양 바꾸는 커밋, 그다음 뒤따르는 정리. One commit per accepted fix, staging only the files you changed (git add <files>, never -A). 받아들인 고침 하나에 커밋 하나. 내가 바꾼 파일만 stage 한다. git add -A 는 쓰지 않는다. Commit uncommitted edits as one clear wip: commit on the current branch so nothing is lost. 커밋 안 된 편집은 지금 브랜치에 wip: 커밋 하나로 분명히 남겨 아무것도 잃지 않게 한다. playbooks/bug-fix.md 11번 줄 · refactoring.md 14번 줄 · hillclimb.md 15번 줄 · pause-safely.md 7번 줄

큰 PR 하나보다 좁은 PR 다섯. 사슬(stack)로 잇는다

Prefer five narrow PRs to one large PR. A stack is a base-branch chain. The root PR targets trunk. Each child branch rebases onto its parent's exact tip and its PR targets the parent branch. 큰 PR 하나보다 좁은 PR 다섯을 택한다. stack 이란 base 브랜치를 사슬로 이은 것이다. 맨 아래 PR 은 main 을 향한다. 그 위의 브랜치는 각각 바로 아래 브랜치의 끝 커밋 위로 rebase 하고, 그 PR 은 바로 아래 브랜치를 향한다. playbooks/opening-a-pr.md 27번 줄

PR 본문은 브리핑이고, 그것이 squash 커밋의 본문이 된다

The PR body is a briefing, not the lab notebook. A reviewer who has the diff should learn why the change exists, what is out of scope, and how you proved the change works. If the body would make the squash commit longer than about 40 lines, cut the body. PR 본문은 브리핑이지 실험 노트가 아니다. diff 를 앞에 둔 리뷰어가 왜 이 변경이 있는지, 무엇이 범위 밖인지, 이 변경이 되는 걸 어떻게 증명했는지를 알 수 있어야 한다. 본문 때문에 squash 커밋이 40줄쯤을 넘으면 본문을 줄인다. playbooks/opening-a-pr.md 13번·15~21번 줄
