# 2026 NGDB 저장소: LLM이 만든 KG를 저장·질의·보완하는 법

조사일은 2026-10-10이다. 대상은 HKUST-KnowComp에서 2026년에 push가 있었던 NGDB 갈래 저장소 다섯 개다.
이 보고서는 "LLM으로 만든 KG를 어떻게 싣고, 묻고, 빈 곳을 채우는가"라는 질문 하나로 다섯 저장소를 본다.

## 읽는 법

- 경로는 `knowcomp-kg-landscape/lab/` 기준이다. `repos/…`는 클론한 코드이고, `sources/05-ngdb/…`는 원자료다. 출처 목록은 `sources/05-ngdb/INDEX.md`에 있다.
- `파일:L12`는 그 파일의 12번째 줄을 뜻한다. 논문 텍스트(`sources/05-ngdb/papers/*.txt`)는 arXiv HTML을 텍스트로 바꾼 것이다. 표는 칸마다 줄이 나뉘어 있다.
- `[확인]`은 코드·논문·데이터 파일을 직접 읽거나 세어서 본 것이다. `[추정]`은 거기서 끌어낸 것이고, 근거를 붙인다.
- 실행은 하지 않았다. 설치·학습·Neo4j 적재는 모두 미검증이다.

용어 세 개를 먼저 정해 둔다.
- **LPG**(Labeled Property Graph): 노드·엣지에 라벨과 속성을 붙이는 그래프 모델이다. Neo4j가 이 모델을 쓰고, 질의 언어는 Cypher다.
- **CQA**(complex query answering): 빠진 엣지가 있는 KG에서 "A와 관련된 B 중 C가 아닌 것" 같은 논리 질의에 답하는 과제다. 1-hop만 묻는 것은 link prediction이다.
- **AutoSchemaKG**: 같은 연구실의 LLM 기반 KG 구축 도구다. 텍스트 조각마다 entity–relation, event–entity, event–relation triple을 뽑고, concept를 붙인다. 산출물 묶음 이름이 ATLAS다.

## NGDBench

### 1. 입력 → 출력

[확인] 다섯 단계다. 논문은 그림 2와 3.1~3.3절(`papers/ngdbench.txt:L212-L364`)에서 설명한다.

| 단계 | 하는 일 | 코드 |
|---|---|---|
| ① 그래프 만들기 | 정형 데이터(LDBC-BI, LDBC-Fin, PrimeKG)는 LPG로 바꾼다. 비정형(Toucan MCP 궤적, LongBench 연차보고서)은 AutoSchemaKG로 추출한다 | `repos/NGDBench/data_gen/graph_gen/dataload_toolkit.py`, `dataload_autokg.py` |
| ② 노이즈 넣기 | 정형 그래프에만 6종 노이즈를 넣고 기록을 남긴다 | `data_gen/graph_generator.py`, `data_gen/perturbation_generator/graph_perturbation.py` |
| ③ Neo4j 적재 | NetworkX 그래프(`.gpickle`/`.graphml`)를 배치 MERGE로 올린다 | `pipeline/db_builder/build_base.py` |
| ④ 질의 생성 | Neo4j에서 schema를 읽고 Cypher 템플릿을 채워 실행한다 | `pipeline/query_gen/qgen_test.py`, `generator/query_generator.py` |
| ⑤ 데이터셋 조립 | 노이즈 그래프에서도 실행해 깨끗한 답과 비교한다. LLM으로 자연어 질문을 붙이고, 비정형은 근거 문단을 붙인다 | `pipeline/dataset_constructor/cli.py` |

**KG 추출 파일 형식.** 비정형 그래프는 AutoSchemaKG 산출물을 그대로 받는다.
- [확인] `dataload_autokg.py:L41-L50`이 받는 파일 이름은 AutoSchemaKG의 CSV 묶음이다. `triple_nodes_*_from_json_without_emb.csv`, `text_nodes_*`, `triple_edges_*`, `text_edges_*`, `concept_nodes_*`, `concept_edges_*`다.
- [확인] 노드 종류는 셋이다. CSV의 `type` 칸(entity/event)을 그대로 쓰고(`:L178`), 원문 조각은 `type="passage"`(`:L187`), concept는 `type="concept"`(`:L196`)다.
- [확인] 엣지는 셋이다. triple 엣지는 LLM이 쓴 relation 문자열을 `relation` 속성에 담는다(`:L205`). entity→passage는 `"mention in"`이다(`:L227`). triple 엣지의 concept 목록은 엣지 속성 `concepts`로 붙는다(`:L211-L218`).
- [확인] Hugging Face의 Econ 추출 원본은 JSONL이다. 레코드 하나가 텍스트 조각 하나이고 키는 `original_text`, `entity_relation_dict`(`Head/Relation/Tail`), `event_entity_dict`(`Event/Entity[]`), `event_relation_dict`다(`sources/05-ngdb/hf-ngdbench/econ_extraction_sample.json`).
- [확인] MCP 추출 원본은 기본 키 대신 `tool_sequence_extraction_dict`(`subject/relation/object`)를 쓴다. 같은 파일에 첫 레코드를 저장해 두었다. `pipeline/dataset_constructor/mcp_mentions.py:L14-L17`이 이 키 이름을 읽는다. [추정] MCP용으로 추출 프롬프트를 바꿨다 — 근거: AutoSchemaKG 기본 키 셋이 없고 새 키가 있다.

**Neo4j 적재.**
- [확인] 모든 노드에 공통 라벨 `NGDBNode`를 붙인다(`build_base.py:L30`). `_node_id`에 unique constraint를 건다(`:L165-L168`).
- [확인] 노드는 `UNWIND … MERGE (n:{label} {_node_id})`, 엣지는 `MERGE (s)-[r:{rel_type} {_edge_id}]->(t)`로 올린다(`:L253-L254`, `:L301-L303`).
- [확인] 노드 라벨은 `label`→`type`→`node_type` 순으로 고른다(`:L311`). 엣지 타입은 `relation`→`label`→`type` 순이다(`:L319`). 영숫자·밑줄 아닌 글자는 `_`로 바뀐다(`:L328-L332`).
- [추정] 그래서 AutoSchemaKG 그래프는 Neo4j에서 라벨 `entity`/`event`/`passage`/`concept`가 되고, LLM이 쓴 relation 문자열이 그대로 relationship type이 된다. `"mention in"`은 `mention_in`이 된다 — 근거: 위 sanitize 규칙과, `pipeline/dataset_constructor/unstructured.py:L215-L217`의 질의 `MATCH (n)-[:mention_in]->(m) WHERE n.id IN $node_ids`.
- [확인] 실제 생성된 MCP 질의가 이 모양을 보여 준다. 예는 `MATCH (n:event {parameter: [...]})-[:has_concept]->(m) RETURN m`이다(`repos/NGDBench/pipeline/query_gen/query/mcp_tool/query_results_mcp1_cleaned.json`, 332개).

**Text-to-Cypher / GraphRAG 평가.**
- [확인] 이 저장소에는 평가 실행 코드가 없다. `graphrag|hipporag|text2cypher|qwen3`를 `.py`에서 찾으면 주석 한 줄만 나온다. README도 생성 파이프라인만 다룬다.
- [확인] 평가 방법은 논문에만 있다. 정형 데이터는 oracle Cypher를 깨끗한 그래프에서 돌린 답이 정답이다(`ngdbench.txt:L598`). Text-to-Cypher(Neo4j-Text2Cypher, GPT-5.1-Codex, DeepSeek V3.2, Qwen3-Coder-480B)와 GraphRAG(Qwen3-0.6B dense triple retriever, top-15)가 노이즈 그래프 위에서 답한다(`:L604-L606`).
- [확인] 비정형 데이터에는 깨끗한 그래프가 없다. GraphRAG, HippoRAG2, ToG를 비교한다(`:L619`). 정답은 추출 KG에 Cypher를 실행한 답이다. 그 답이 원문 근거(`mention_in_nodes`)로 뒷받침되는지 LLM이 `true/false/incomplete/unknown`으로 판정한다(`pipeline/dataset_constructor/unstructured_answer_judge.py:L20`, README의 `answer-judge` 절).

| 비정형 정답 판정 | 옛 스크립트 기본값 gpt-5 | 프롬프팅 | [확인] `pipeline/handler/unstructured_valid.py:L385` |

### 3. schema

- [확인] 정형 데이터는 고정 schema다. YAML이 허용 (src, rel, dst)를 정한다. PrimeKG는 노드 타입 10종이다(`pipeline/query_gen/schema/ngdprime_schema.yaml`). 노이즈가 만든 불법 조합을 이 YAML로 걸러 낸다(`generator/query_generator.py:L267-L279`).
- [확인] 비정형 데이터에는 YAML이 없다. DB에서 읽은 schema를 그대로 쓴다(`:L308-L309`의 경고 분기).
- [확인] 노드 타입은 entity/event/passage/concept 넷이다. relation은 LLM이 쓴 자유 문자열이다. Econ 추출 파일 하나(664조각)에서 entity relation 문자열이 3,493종이다. "based on" 72, "based upon" 95, "is based on" 89, "is based upon" 56처럼 같은 뜻이 갈라져 있다(`hf-ngdbench/econ_extraction_sample.json`의 `econ_stats`).
- [확인] MCP 그래프는 사후 정규화를 한 번 거친다. `has_parameter`, `hasParameters`, `接收参数` 같은 변형을 `parameter`·`return`·`type`·`description` 노드 속성으로 접는다(`data_gen/graph_gen/dataload_clean.py:L61-L72`). concept 노드를 지우고 이웃 속성으로 옮기는 함수도 있다(`:L256`).

### 4. 품질 관리

- [확인] 정형 그래프에는 노이즈를 일부러 넣는다. 6종의 기본 비율은 엣지 누락 5%, 가짜 엣지 10%, relation 오분류 10%, 노드 타입 오류 10%, 이름 오타 20%, 속성 오류 10%다(`perturb_guide/general_guid_new.json:L37-L44`). 무엇을 바꿨는지 기록 파일로 남긴다.
- [확인] 비정형 그래프에는 노이즈를 더하지 않는다. "자동 추출 결과가 이미 중복·표기 변이·relation 오류·타입 오류를 담고 있다"고 본다(`ngdbench.txt:L347`).
- [확인] 그래서 비정형 쪽 품질 장치는 하나다. 답마다 원문 근거를 붙이고 LLM이 판정한다(위 1절).
- [확인] 논문은 한계를 적는다. 추출 KG의 생성·수정·삭제 질의는 아직 없다. 추출 KG 편집에는 사실 근거와 도메인 검증이 필요하다는 이유다(`ngdbench.txt:L648`).

### 5. 저장·질의

- [확인] 저장은 Neo4j 5.x이고 질의는 Cypher 전체다. 23개 분석 연산자와 5개 관리 연산자를 템플릿으로 덮는다(`ngdbench.txt:L359`). 집계(SUM/COUNT/MIN/MAX/AVG), 가변 길이 경로, CREATE/MERGE/SET/DELETE가 들어간다.
- [확인] 답이 32개 이상인 비집계 질의는 Boolean 확인 질문으로 바꾼다(`ngdbench.txt:L364`).
- [확인] "neural" 추론 엔진은 이 저장소에 없다. 벤치마크는 그런 엔진이 필요하다는 것을 보이는 쪽이다.

### 9. 이 저장소가 말하는 "LLM 시대 KG"

LLM이 텍스트에서 뽑은 KG는 Neo4j LPG로 싣고 Cypher로 묻는다. 다만 관측 그래프는 노이즈 낀 사본이다. 그래서 그 위에서 실제 상태를 추론하는 neural 질의가 필요하다.

## NGDB-Zoo (neural_graph_db_training)

### 1. 입력 → 출력

- [확인] 입력은 SMORE 형식의 ID triple이다. `stats.txt`(entity 수, relation 수)와 `{train,valid,test}_bidir.txt`를 C++ 바이너리로 굽는다(`repos/neural_graph_db_training/ngdb_zoo/cpp_sampler/cook_kg.py:L28-L37`). 엔티티 이름표는 `id2ent.pkl`이다.
- [확인] 학습 중 C++ sampler가 질의를 온라인으로 뽑는다(`config.py`의 `--online_sample`). 질의는 operator DAG로 쪼개져 operator 종류별로 묶여 실행된다(`training/query_dag.py`, `training/operator_scheduler.py`).
- [확인] 출력은 학습된 query encoder 체크포인트와 MRR이다. 서빙이나 질의 API는 없다.
- [확인] **ATLAS-Wiki 사용.** 코드에는 ATLAS 전용 로더가 없다. `atlas`를 grep하면 나오지 않는다. [확인] 논문은 ATLAS-Wiki-Triple-4M을 대규모 벤치마크 셋 중 하나로 쓴다(`papers/ngdb-zoo.txt:L274`, `:L598`). entity 4,035,238개, relation 512,064개, 엣지 28,801,086개다(`:L1106-L1108`). 질의는 degree-weighted edge sampling으로 뽑았다(`:L274`). 더 작은 6.4% 표본도 만들었다(`:L1062`). ### 2. LLM의 역할

### 3. schema

해당 없음. [확인] 입력은 relation ID가 붙은 triple뿐이다.

### 4. 품질 관리

### 9. "LLM 시대 KG"의 핵심

LLM이 만든 거대하고 희소한 KG에서도 query encoder를 빠르게 학습하려면, operator 단위 batching과 미리 계산한 텍스트 임베딩이 필요하다.

## KGPFN

### 1. 입력 → 출력

- [확인] 입력은 데이터셋마다 `train.txt`, `valid.txt`, `test.txt`의 (h, r, t) 문자열 triple이다(`repos/KGPFN/pfn/datasets.py:L994-L1013`의 `TransductiveDataset`). 처리 결과는 PyG `Data`다. 역관계를 붙여 relation 수가 두 배가 된다(`:L1052-L1090`).
- [확인] 질의 (h, r, ?)마다 두 맥락을 만든다. 첫째는 국소 맥락이다. head 주변을 NBFNet으로 3-hop 인코딩한다. 둘째는 전역 맥락이다. 같은 relation의 양성 20개와 음성 80개를 KG에서 꺼낸다(`papers/kgpfn.txt:L222-L224`). 음성의 약 80%는 head의 2-hop 이웃에서 뽑는다(`:L1540`).
- [확인] PFN Transformer(TabICL 가중치로 시작)가 후보 tail마다 점수를 낸다. 출력은 순위다.

**새 KG에 학습 없이 붙는가.**
- [확인] 붙는다. "fine-tuning 없이" 평가에서 사전학습한 모델은 대상 그래프의 보이는 엣지에서 맥락을 꺼내 고정 파라미터로 예측한다(`kgpfn.txt:L227`). 사전학습은 FB15k-237, WN18RR, CoDEx-Medium 세 그래프에만 했다.
- [확인] 코드도 그렇게 돈다. `config/script/test.yaml:L67`이 `num_epoch: 0`이다. `script/test_kgpfn.py:L604-L605`는 epoch가 0이면 학습 루프를 건너뛴다.
- [확인] 조건이 둘 있다. 첫째, 대상 KG가 데이터셋 클래스로 등록돼 있어야 한다(`pfn/datasets.py:L3648-L3659`의 `JointDataset.datasets_map`). 사용자 KG를 넣으려면 클래스를 하나 써야 한다. 둘째, 질의하는 relation의 다른 사례가 그 KG에 있어야 전역 맥락이 생긴다. 양성이 20개보다 적으면 빈자리를 음성으로 채운다(`kgpfn.txt:L1540`).

### 2. LLM의 역할

- [확인] 생성형 LLM은 없다.
- [확인] 코드에는 문장 encoder(all-MiniLM-L12-v2)를 쓰는 변형 `iclsemantic`이 있다(`config/kgpfn/kgpfn_iclsemantic.yaml:L28`, `model/kgpfnsem.py`). 공개 체크포인트에도 `kgpfn_iclsemantic.pth`가 있다(HF `Eason-nuo/KGPFN`).

### 3. schema

해당 없음. [확인] relation은 ID이다. 처음 보는 relation도 relation graph 위 message passing으로 표현을 만든다(ULTRA 방식, `kgpfn.txt:L144`).

### 4. 품질 관리

해당 없음. [확인] 논문은 KG를 불완전하다고 보고 빠진 tail을 예측한다. 틀린 엣지를 다루는 장치는 없다.

## 갈래 종합

### 이 갈래가 2026년에 권하는 저장·질의 방식

[확인] 다섯 저장소 어디에도 "이 스택을 쓰라"는 처방은 없다. 아래는 저장소들이 실제로 한 일에서 끌어낸 그림이다.

1. **저장은 Neo4j LPG다.** [확인] LLM 추출 KG를 실제로 DB에 올린 곳은 NGDBench 하나다. AutoSchemaKG CSV → NetworkX → Neo4j 순서를 밟는다. entity·event·passage·concept가 노드이고, 원문 조각과 `mention_in` 엣지로 이어진다.
2. **질의는 Cypher다. 원문 근거를 같이 끈다.** [확인] 비정형 데이터에서는 Cypher 답에 `mention_in` 원문을 붙인다. LLM이 그 근거로 답을 판정한다. [확인] 논문 결과에서 추출 triple 직접 검색(GraphRAG)이 원문 기반 RAG보다 낫다. 그래도 F1이 0.25를 넘지 못한다.
3. **보완(빈 엣지 채우기)은 아직 별도 모듈이다.** [확인] 빈 곳을 채우는 모델은 KGPFN(link prediction), NGDB-Zoo(query encoder), NS3·NLISA(CQA)다. 이들은 모두 ID triple을 받는다. Neo4j와 잇는 코드는 없다. [추정] 갈래의 방향은 "Neo4j 같은 기호 저장소 + 그 위의 neural 추론"이다. 그러나 2026년 현재 둘을 묶은 엔진은 공개되지 않았다 — 근거: NGDBench는 엔진 없이 문제만 제시한다. 엔진 저장소(KnovexDB)는 2025-06 이후 멈췄다(이전 보고).

| KGPFN | 학습 없이 빠진 tail 예측 | triple을 `train/valid/test.txt`로 내보내고 데이터셋 클래스를 하나 쓴다 | [추정] 보완용으로 가장 싸다. 단, LLM 추출 KG에서 검증된 적이 없다 |
| NGDB-Zoo의 텍스트 임베딩 결합 | 엔티티 이름의 의미를 구조 임베딩에 더하기 | SMORE 형식 변환이 필요하다. 공개 모델은 셋뿐이다 | [추정] 아이디어(오프라인 임베딩 후 이어 붙이기)만 가져가는 편이 낫다 |
| NS3 · NLISA | 다단 논리 질의 응답 | KGE와 LMPNN을 먼저 학습해야 한다. NLISA는 checkpoint가 미공개다 | [추정] 지금 사용자 KG에 붙이기에는 무겁다 |

### 붙이기 전에 걸리는 것

[추정] 가장 먼저 걸리는 것은 relation 어휘다. 근거가 둘이다.
- [확인] Econ 추출 664조각에서 relation 문자열이 3,493종이다. 같은 뜻이 표기만 달리 갈라진다.
- [확인] ATLAS-Wiki(relation 512,064종)에서 query encoder MRR은 7~9%다. ogbl-wikikg2(535종)에서는 33~45%다.

[확인] NGDBench도 MCP 그래프에서 relation 변형을 손으로 접었다(`dataload_clean.py:L61-L72`). [추정] 그러니 neural 보완 모듈을 붙이기 전에 relation 정규화(동의어 병합이나 concept 단위 묶기)가 필요하다. relation ID가 수천~수십만 개면 link prediction과 CQA가 모두 약해진다. 정규화가 얼마나 도움이 되는지 잰 실험은 다섯 저장소 어디에도 없다.

## 확인 못 한 것

- 실행. 다섯 저장소 모두 설치·실행하지 않았다. 최소 실행 경로는 코드와 README에서 끌어냈다.
- NGDBench 추출에 쓴 LLM. Qwen2.5-14B-Instruct는 HF 파일 이름에서만 나온다. 논문과 코드는 모델과 AutoSchemaKG 설정을 밝히지 않는다.
- NGDBench 평가 코드. Text-to-Cypher·GraphRAG 실행 코드, 프롬프트, Qwen3-0.6B retriever 설정은 저장소에 없다. 논문 수치를 재현할 수 없다.
- NGDB-Zoo의 ATLAS-Wiki 전처리. ID 변환, 질의 샘플링, 텍스트 prior를 쓴 ATLAS 실험은 코드와 논문 어디에도 없다.
- NGDB-Zoo README의 FuzzQE·Q2P·RotatE 지원. 공개 코드에서 찾지 못했다. 다른 브랜치나 원본 저장소(zhongweixie)는 보지 않았다.
- KGPFN semantic 변형의 성능. 체크포인트는 있다. 논문 수치는 없다.
- 학회 채택. NGDBench, NGDB-Zoo, KGPFN은 arXiv에 학회 표기가 없다. NS3·NLISA의 KDD 2026은 PDF의 ACM 인용 형식에서만 봤다(이전 보고).
- MCP 추출 원본(808MB)은 첫 레코드만 봤다. relation 종류 수는 Econ 파일에서만 셌다.
