# LLM 시대 KG 만들기 — KnowComp 2026 저장소를 코드로 읽기

조사일: 2026-10-10. 대상은 2026 년에 push 가 있는 다섯 저장소다: AutoSchemaKG, AtlasKV, DeepRefine, DeepRefine-Skill, EvolvingWorld. AutoGraph-R1(마지막 push 2025-11)은 DeepRefine 의 바탕이라 비교 기준으로만 쓴다.

## 결론

- [확인] 이 갈래가 2026 년에 권하는 구축 방식은 하나가 아니다. 다섯 저장소가 KG 의 서로 다른 단계를 맡는다. 뽑기(AutoSchemaKG), 고치기(DeepRefine·DeepRefine-Skill), LLM 에 넣기(AtlasKV)다. EvolvingWorld 는 KG 가 아니다.
- [추정] 그래도 공통 방향은 하나로 읽힌다. "싸게 뽑고, 질의가 실패한 곳을 고친다" 이다 — 사례 3개: AutoGraph-R1·DeepRefine 의 초안 KB 는 둘 다 개념을 끄고 트리플 프롬프트 한 장으로 뽑는다. DeepRefine 논문은 재구축 대신 "post-construction refinement" 를 내세운다. DeepRefine-Skill 은 질의 로그로 그래프를 고친다.
- [확인] 사용자가 지금 실제로 돌릴 수 있는 경로는 둘이다. atlas-rag 로 뽑기(사용자가 이미 Ollama Llama 3.1 8B 로 돌렸다)와, DeepRefine-Skill 의 agent 모드로 고치기(stdlib 만으로 review·apply 가 돈다)다. DeepRefine 학습 경로와 AtlasKV 는 GPU 서버 여럿과 하드코딩된 경로를 고쳐야 한다.

## AutoSchemaKG (atlas-rag)

### 입력 → 출력

1. [확인] 문서 JSON/JSONL 을 `load_dataset` 으로 읽는다(`ASK/atlas_rag/kg_construction/triple_extraction.py:307-322`). 청크는 기본 8,192자, overlap 0 이다(`triple_config.py:34-35`).
2. [확인] `run_extraction`(`triple_extraction.py:380`)이 청크마다 메시지 셋을 만든다(`create_batch_instructions`, `:213`). 출력은 `json_repair.loads` 로 고친다(`:256`).
3. [확인] `convert_json_to_csv`(`:454`)가 공백 정리 후 글자가 같은 노드만 합친다(`utils/json_processing/json_to_csv.py:20,33`).
4. [확인] `generate_concept_csv_temp`(`:468`) → `create_concept_csv`(`:490`)가 개념 이름표를 붙인다. `include_concept` 기본값은 True 다(`triple_config.py:23`).
5. [확인] `convert_to_graphml`(`:504`)이 `nx.DiGraph` 로 저장한다(`utils/csv_processing/csv_to_graphml.py:132`). `compute_kg_embedding`(`:527`)이 FAISS 색인을 만든다.

### 나머지 틀

- LLM: [확인] ATLAS 는 Llama-3-8B-instruct 로 지었다(`ASK-ACL:1999`). 학습은 없다.
- schema: [확인] 기본 schema 는 세 단계(엔티티-엔티티, 이벤트-엔티티, 이벤트-이벤트)다. 2025-08 부터 `triple_extraction_prompt_path`·`triple_extraction_schema_path` 로 단계와 필드를 사용자가 바꿀 수 있다(`triple_extraction.py:277-302`). 2026-01 에 필드마다 `node_type` 을 줄 수 있게 됐다. 문서는 "Schema Induction (Concept Generation) and retrievers may not handle node_type other than "entity" or "event" properly" 라고 경고한다(`ASK/docs/source/example/advance_features.md:37`).
- 품질 관리: [확인] 검증 단계가 없다. custom schema 는 relation 필드가 있는지와 필드 수만 검사한다(`triple_extraction.py:298-302`).
- 저장·질의: [확인] HippoRAG2 는 방향 그래프에 `nx.pagerank` 를 돈다(`ASK/atlas_rag/retriever/hipporag2.py:270`). 평가 코드 기본은 개념을 쓰지 않는다(`ASK/atlas_rag/evaluation/benchmark.py:55`). billion-scale 은 Neo4j + `lkg_retriever/` 로 호스팅한다.
- 평가: [확인] 8B 로 지은 KG + HippoRAG2 의 Full-KG 가 MuSiQue/2Wiki/HotpotQA EM 31.8/65.3/61.8 이다(`ASK-ACL:613`). 원 HippoRAG2(70B 구축)는 37.2/65.0/62.7 이다(`:595`). GraphRAG 27.3/51.4/55.2(`:591`), LightRAG 20.0/38.6/33.3(`:592`)보다 높다. 개념을 뺀 Entity-KG 는 31.4/64.2/60.9 다(`:611`).
- 규모·비용: [확인] 5천만 문서 이상(`ASK-ACL:29`), 총 78,400 GPU 시간(`:2014`)이다. En-Wiki 는 243.9M 노드·1.49B 엣지에 14,300 시간, CC 는 937.3M 노드·5.96B 엣지에 52,300 시간이다(`:2000-2013`).
- 지금 쓰나: [확인] `pip install atlas-rag`(0.0.5.post1, Python ≥3.9, MIT). 사용자가 Ollama Llama 3.1 8B 로 공식 변환 경로를 이미 돌렸다(autoschemakg 노트 `09_official_graph.py`).
- 유지보수: [확인] `release/v0.0.6` 브랜치(로컬에 `origin/release/v0.0.6` 으로 받음, working tree 는 그대로)가 main 보다 3 커밋 앞선다. 고친 것은 넷이다. 개념 샤딩 전 `random.shuffle` 제거(이슈 #42), 엣지가 가리키는 노드가 노드 CSV 에 없을 때 `type="Unknown"` 으로 추가(#45), 임베딩 두 번 호출 제거(#44), `get_node_id` 의 mutable default `entity_to_id={}` 제거다. 이 브랜치는 PyPI 에 없다.

핵심 한 문장: [추정] 사람이 칸을 짜지 않고 LLM 프롬프트로 엔티티·사건·개념을 웹 규모로 뽑아, 검색 그래프로 쓴다 — 근거: 위 파이프라인과 ACL §1.

## AtlasKV

### 입력 → 출력

1. [확인] AutoSchemaKG 의 `triple_edges*.csv` 를 head·tail·relation 순서로 읽는다(`AKV/dataset_generation/build_atlas_training_data.py:206`). `concepts`·`synsets`·`:TYPE` 열은 버린다.
2. [확인] KG2KV: head 나 tail 하나를 무작위로 가린다(`:215`). GPT-4o-mini 가 relation 을 명사로 바꾼다(`:83-124,144-155`). key 는 "the {relation_nl} of {name}", value 는 가린 엔티티다(`:242-264`).
3. [확인] `generate_kb_embeddings_gmm.py` 가 key·value 를 sentence encoder 로 임베딩해 `.npy` 로 저장한다(`:497-597`). `--cluster` 면 UMAP 뒤 GMM 2단으로 root·inter·leaf 트리를 만든다(`:418,438-455`).
4. [확인] 모델은 3층마다 KB 전용 query head `q_proj_kg` 를 둔다(`AKV/src/atlaskv/models/llama3_model.py:121,307`). KB key/value 가 attention 에 따로 붙는다. KB 는 context 토큰이 아니다.
5. [확인] HiKVP 는 eval 에서만 돈다. root → inter → leaf 로 top-k 128/64/16 을 골라 GPU 로 올린다(`llama3_model.py:507-575`, `experiments/eval.py:641-643`).

### 나머지 틀

- LLM: [확인] 백본은 LLaMA3.1-8B-Instruct 이고 동결한다(`AKV/experiments/train.py:246-247,929`). `q_proj_kg` 와 projector 만 학습한다(`train.py:603-627`, `src/atlaskv/kb_encoder.py:99-108`).
- schema: [확인] 없다. 논문도 트리플을 독립 사실로 "flatten" 해 multi-hop 을 막는다고 한계로 적는다(`AKV.txt:1472-1475`).
- 품질 관리: [확인] 한 번 본 엔티티가 나오면 그 트리플을 버린다(`build_atlas_training_data.py:169-171,211-213`). 이름 4단어 미만, value 10–20단어만 남긴다(`:173-191`).
- 평가: [확인] 정답이 KB 안에 있는 조건에서 15번째 층 KB attention 의 argmax 를 본다(ACC). ATLAS-CC 10³ 트리플 ACC@1 은 KBLaM 12.7, AtlasKV(HiKVP) 61.8, HiKVP 없이 83.6 이다. 10⁴ 에서는 3.6 / 40.0 / 61.8 이다(`AKV.txt:520-522`). HiKVP 를 켜면 정확도가 떨어진다.
- 규모: [확인] "1B triples, 20GB 미만" 근거는 Figure 4 와 본문뿐이다. 정확도는 10⁴ 트리플까지만 쟀다(`AKV.txt:504-523`). 학습 트리플은 20K 다(`AKV.txt:866`).
- ATLAS-Wiki 크기 엇갈림 해소: [확인] AtlasKV 는 ATLAS-Wiki 를 "900+ million nodes and 5.9 billion edges" 로 적는다(`AKV.txt:421-422`). AutoSchemaKG 부록 기준 En-Wiki 는 1.49B 엣지, 5.96B 는 CC 다(`ASK-ACL:2001,2012-2013`). 그래서 부록의 "1.492B triples"(`AKV.txt:866`)가 Wiki 값이고, 본문 수치는 ATLAS 전체나 CC 값을 옮긴 것이다.
- 지금 쓰나: [확인] MIT 다. 그러나 막는 것이 여럿이다.
  - README 는 `python=3.9`·clone URL `your-repo` 를 안내하는데, 코드는 3.10 문법을 쓴다.
  - 스크립트에 `your_*` 경로가 퍼져 있다.
  - HiKVP 플래그 `--use_hierarchial_kv` 는 기본 False 이고 제공 스크립트 어디서도 켜지 않는다(`eval.py:644`, 스크립트 grep 0건).
  - [추정] HiKVP value 인덱싱 버그가 있다 — 사례 1개: `llama3_model.py:565` 가 부분집합 위치 `top_idx` 를 그대로 쓴다. 같은 파일 `:636` 은 원래 leaf 위치로 바꿔 쓴다.
- 새 지식 추가: [확인] LLM 재학습 없이 KB 행렬에 붙일 수는 있다(`src/atlaskv/utils/train_utils.py:105-128`). 클러스터에 끼워 넣는 코드는 없어 GMM 을 다시 돌려야 한다.

핵심 한 문장: [추정] KG 를 "속성 질의 key → 엔티티 value" 임베딩 쌍으로 펼쳐, 동결 LLM 의 attention 에 붙여 retriever 없이 쓴다 — 근거: 위 #입력 → 출력 4–5.

## DeepRefine

### 입력 → 출력

1. [확인] 초안 KB 는 atlas-rag 로 짓는다. `include_concept=False`, 프롬프트는 schema 없는 subject/relation/object 배열 한 장이다(`DR/benchmark/autograph/custom_kg_extraction.py:34-55`). 기본 구축기는 Qwen2.5-3B 다(`DR/scripts/eval/kg_construction_naivecons.sh:2`).
2. [확인] FAISS `IndexIDMap(IndexFlatIP)` 로 색인한다(`DR/AutoSchemaKG/atlas_rag/vectorstore/create_graph_index.py:41-44`). 이 형태라야 증분 add/remove 가 된다.
3. [확인] `DeepRefine.refine()`(`DR/autorefiner/src/deeprefine.py:323-549`)이 한 대화 안에서 세 걸음을 돈다. answerability 판단(`<judge>`, hop 마다 1-hop 이웃 확장), 결함 추론(`<abduction>`), 편집 생성(`<refinement>`)이다.
4. [확인] 편집은 `_insert_edge`(`:1635-1751`), `_delete_edge`(`:1753-1815`), `_replace_node`(`:1817-1892`)이다. networkx 와 FAISS 를 함께 고친다.
5. [확인] 고친 KB 를 pickle 로 저장한다. passage 노드를 다시 붙여 ToG·Subgraph·HippoRAG2 로 QA 를 돈다(`DR/benchmark/autograph/benchmarking_graph_refiner.py:339-464`).

### 나머지 틀

- LLM: [확인] refiner 는 Qwen3-8B 나 Qwen3-4B-Instruct-2507 을 GRPO 로 학습한다. reader·judge 는 Qwen2.5-7B, 임베딩은 Qwen3-Embedding-0.6B 다(`DR.txt:349-353`). 프롬프트는 `DR/autorefiner/src/rag_server/deeprefine_prompt.py:29-92` 에 있다.
- 보상: [확인] GBD(q) = F1(A_refined, A) − F1(A_draft, A) 이다(`DR.txt:279`). 학습 스크립트의 4분면 값이 이 식과 같게 맞춰져 있다(`DR/scripts/train/run_qwen3-8b_graph_refiner.sh:131-134`).
- schema: [확인] 없다. 노드는 entity·passage, 엣지는 Relation·Source 다. 노드 id 는 `sha256(name+"_entity")` 라 이름이 같아야 같은 노드다(`deeprefine.py:1900-1917`).
- 품질 관리: [확인] grounding·충돌·generic object 필터가 있다(`deeprefine.py:740-865`). 논문 평가 스크립트는 이 필터를 모두 끈다(`benchmarking_graph_refiner.py:293-311`). 사람 개입 지점은 이 저장소에 없다.
- 계약 어긋남: [확인] `delete_edge` 인자가 프롬프트에선 셋(`deeprefine_prompt.py:72`), 재시도 안내에선 둘(`deeprefine.py:730`)이다. 필터는 처음과 끝만 쓴다(`:837`).
- 평가: [확인] 단순 구축기 KB 에 DeepRefine-8B 를 붙이면 ToG 평균 F1 33.01 → 38.61(+5.60), Subgraph 30.82 → 34.87(+4.05)이다(`DR.txt:416-421`). HippoRAG2 는 +1.41 이다. RL 없는 같은 프롬프트와 견주면 8B 36.74 대 35.47 이다(`DR.txt:526-529`). GraphRAG·LightRAG 는 인용만 하고 baseline 이 아니다.
- 비용: [확인] 학습은 8×A800-80GB 다(`DR.txt:357-358`). 추론 시간은 Simple QA 기준 AutoGraph-R1 6,782.8초 대 DeepRefine 3,201.7초다(`DR.txt:492-496`). 학습 시간·토큰은 논문에 없다.
- 지금 쓰나: [확인] MIT, HF `HaoyuHuang2/DeepRefine-v1-8B`, Docker 이미지가 있다. 막는 것은 넷이다.
  - requirements 가 PyPI `atlas-rag==0.0.5` 를 고정하는데, 그 wheel 에는 `use_flat_index` 가 없다. vendored `./AutoSchemaKG` 를 `pip install -e` 해야 한다.

## DeepRefine-Skill

### 입력 → 출력

- 입력: [확인] graphify 의 `graphify-out/graph.json` 과 질의 로그 `graphify-out/memory/query_*.md` 다.
- 출력: [확인] 고친 graph.json, `.deeprefine/` 아래의 이력·trace·review·백업·checkpoint, 선택적으로 다시 만든 wiki 다.

| 걸음 | 하는 일 | 코드 |
|---|---|---|
| 1 | 질의 로그를 `history.jsonl` 로 옮긴다 | `DRS/deeprefine_skill/history.py:144-168` |
| 2 | 최대 4 hop 판단. 1 hop 은 `graphify query`, 이후 graph.json 1-hop 확장 | `claude_skill/references/deeprefine-workflow.md:83-133`, `agent_prompts.py:52-56` |
| 3 | 결함 추론 → 편집 최대 10개 | `agent_loop.py:72-93`, `agent_prompts.py:30-50` |
| 4 | trace 가 제어 흐름을 지켰는지 검사 | `agent_loop.py:121-229` |
| 5 | 편집에 HIGH/MEDIUM/LOW 붙이기. 여기서 멈추고 사람 승인 | `cli.py:544-581`, `action_review.py:263-366` |
| 6 | 승인 뒤 apply. LOW 있으면 거부, 백업·checkpoint | `cli.py:367-541`, `paths.py:77-155` |

### 나머지 틀

- LLM: [확인] agent 모드에서는 호스트 agent(Claude Code 등)의 세션 모델이 판단·추론·편집을 직접 한다. Python 은 LLM 을 부르지 않는다. 프롬프트는 DeepRefine 의 것을 그대로 옮겼다(`agent_prompts.py:3-50`). 학습된 DeepRefine 가중치를 가리키는 곳은 없다. CLI 모드는 OpenAI 호환 API 를 쓰고 기본 모델은 `gpt-4.1-mini` 다(`paths.py:175-195`).
- schema: [확인] graph.json 은 networkx node-link 형식이다. 엣지는 `relation` 과 `confidence`(EXTRACTED·INFERRED·AMBIGUOUS)를 반드시 가진다(`scripts/validate_graph_schema.py:21-26`). relation 이름은 자유 문자열이다. 새 엣지는 `INFERRED`, 0.9, `source_file:"deeprefine"` 로 들어간다(`agent_graph.py:144-157`).
- 품질 관리: [확인] 이미 있는 엣지나 코드 근거가 있으면 HIGH, 양 끝 노드만 있으면 MEDIUM, 근거가 없으면 LOW 다. 새 노드를 만드는 insert 는 LOW 로 막힌다(하위 에이전트가 fixture 로 실행 확인).
- 문서와 코드 차이: [확인] 문서는 "cross-community" 를 LOW 조건으로, MEDIUM 을 "k-hop context supports" 로 설명한다. 코드는 community 를 보지 않고 노드 존재만 본다(`action_review.py:263-366`, `deeprefine-workflow.md:151`).
- 저장·질의: [확인] DB 없이 파일뿐이다. wiki 검색은 substring 점수 + `links_to` BFS 다(`wiki_retrieval.py:63-149`). 임베딩은 쓰지 않는다.
- 평가: [확인] 측정 수치가 없다. `eval/benchmarks/refinement_recall.py:116-125` 는 `NotImplementedError` 골격이다. 유일한 크기 기록은 저장소 자신을 graphify AST 모드로 만든 노드 361·엣지 646 이다(`docs/phase-b-report.md:7,45-48`). LLM 추출 엣지(INFERRED) 정제는 "Not tested" 다(`:95`).
- graphify 의 역할: [확인] `graphify update` 는 tree-sitter AST 만 쓴다. `graphify extract` 는 여기에 LLM 추출을 더해 INFERRED 엣지를 만든다(`docs/phase-b-report.md:21-27,79-86`). 코드베이스가 1차 대상이다.
- 지금 쓰나: [확인] MIT, Python ≥3.10, 선언 의존성은 `openai` 하나다. agent 모드는 stdlib 만으로 돈다(하위 에이전트가 review·apply·LOW guard·rollback 을 실행 확인).
- Obsidian 경로: [확인] `wiki_importer`·`wiki_retrieval` 은 `cli.py` 에 연결되지 않았다. Python 에서 직접 불러야 한다. 만든 그래프는 relation 이 `links_to` 하나뿐이고 저장소 자체 validator 를 통과하지 못한다(하위 에이전트 실행).
- `--update-wiki` 버그: [확인] `.md` 만 고치고 graph.json 은 그대로 둔 채 checkpoint 를 만든다(`cli.py:474-489` 가 `apply_refinement_text` 를 부르지 않음, 하위 에이전트가 md5 로 실행 확인).

핵심 한 문장: [추정] KG 를 질의 로그 기반으로 계속 유지보수하는 산출물로 보고, 코딩 agent 가 "답할 수 있나 → 왜 못 했나 → 어느 엣지를 고칠까" 를 추론하게 하되, 증거 등급·사람 승인·rollback 으로 감싼다 — 근거: 위 표.

## EvolvingWorld

- KG 인가: [확인] 아니다. 인물·장소마다 텍스트 카드(Markdown)를 두고 장면 단위로 통째로 다시 쓴 이력이다. typed edge·트리플·relation 테이블이 없다. 관계는 프로필 안 "Key Relationships" 같은 텍스트로만 있다(`EW/data_construction/main.py:1952-1959`).
- 입력 → 출력: [확인] 책 JSONL → 장면 추출(약 1,500 토큰 청크) → 인물 이름 정규화(alias) → 인물 프로필 초기화·변화 → 장소 추출·정규화 → 세계·장소 카드 → SFT 데이터(`main.py:4194-4206` 의 `process_book`).
- LLM: [확인] 추출은 `gemini-2.5-pro`, 실패하면 `claude-sonnet-4-5` 다(`main.py:29-32`). World Model·Character Agent 는 LLaMA-Factory LoRA 로 학습한다(`EW/training/train_config.yaml:35-92`).
- open-schema 의 실체: [확인] 참고용 dimension 힌트를 주고 LLM 이 고르거나 합치거나 새로 만든다. 논문 집계로 인물 dimension 581종, 세계 dimension 136종이다(`EW.txt:1608-1612`). 고정 schema 로 바꾼 ablation 은 GPT-5.3-Chat 하나로 쟀다(`EW.txt:2568-2582`).
- 사용자 과제에 쓸 것: [추정] alias 해소와 "앞 장면을 보고 상태를 갱신하는" 패턴, 약한 신호를 모아 두는 hidden tracker 정도다 — 근거: 모든 프롬프트가 장면·인물·대사를 전제하고, 논문도 "chronologically narrated" 책을 전제한다(`EW.txt:1356-1360`).
- 규모: [확인] 책 57권, 장면 9,763개, 인물 3,311명, 장소 1,888곳, 학습 샘플 138,596개다(`EW.txt:1390-1399`). GPU·API 비용은 적혀 있지 않다.
- 지금 쓰나: [확인] LICENSE 파일이 없다. HF 데이터셋은 "non-commercial academic research" 라고만 적는다. 커밋 2개, 테스트 없음이다.

## 갈래 종합

### 권하는 방식은 하나인가

[확인] 하나가 아니다. 다섯 저장소가 맡은 단계가 다르다.

| 단계 | 저장소 | 이 단계에서 권하는 것 |
|---|---|---|
| 뽑기 | AutoSchemaKG | 프롬프트 파이프라인. 이벤트·개념까지 뽑을 수 있다 |
| 뽑기(학습) | AutoGraph-R1 (비교) | 구축기 자체를 downstream 보상으로 RL |
| 고치기(학습) | DeepRefine | 질의 실패 지점을 RL 정책으로 국소 편집 |
| 고치기(agent) | DeepRefine-Skill | 같은 프롬프트를 코딩 agent 가 수행, 사람이 승인 |
| LLM 에 넣기 | AtlasKV | 검색 없이 KV 로 attention 에 주입 |
| (KG 아님) | EvolvingWorld | 엔티티별 open-schema 텍스트 카드 |

공통점은 셋이다.

- [확인] relation 은 셋 다 자유 문자열이다(AutoSchemaKG 기본 prompt, DeepRefine 초안 prompt, graphify). 사람이 짠 relation 목록을 쓰는 곳이 없다.
- [확인] 엔티티 병합은 셋 다 글자 일치다. AutoSchemaKG 는 공백 정리 뒤 문자열 비교, DeepRefine 은 `sha256(name)`, AtlasKV 는 중복 엔티티를 버린다. 의미로 같은 것을 묶는 entity resolution 단계는 어느 코드에도 없다. DeepRefine 의 `replace_node` 가 사후에 고치는 유일한 장치다.
- [확인] "좋다" 의 기준은 다섯 중 넷이 downstream QA 점수다(EM/F1, ACC, 판정 점수). KG 자체의 정확도를 사람이 잰 곳은 없다.

[추정] 2026 년의 무게는 "고치기" 쪽에 있다 — 사례 3개: DeepRefine 과 DeepRefine-Skill 이 2026 커밋의 대부분이다(38 + 85). 초안 KB 를 일부러 단순하게(개념 끔, 트리플 한 장) 짓는다. AutoSchemaKG main 은 2026-01 이후 멈췄다.

## 확인 못 한 것

- DeepRefine 학습된 8B 가 범용 모델(gpt-4.1-mini, Claude) 대비 얼마나 나은지. 논문 비교는 같은 크기의 RL 없는 모델뿐이다(`DR.txt:526-529`).
- DeepRefine-Skill 의 정제가 실제로 QA 를 낫게 하는지. 측정이 없다. 회귀 질의 재실행은 OpenCode 어댑터에만 있다.
- AtlasKV 1B 트리플 메모리 수치를 이 코드로 재현할 수 있는지. 하위 에이전트 추정으로는 projected key 만 수십 TB 가 든다(`train.py:262`, `kb_encoder.py:157` 기준 계산). 외삽인지 다른 경로인지 논문에서 찾지 못했다.
- AtlasKV eval 스크립트가 `.jsonl` 을 넘기고 `eval.py:303` 이 `json.load` 로 읽는 문제가 실제로 실패하는지. 실행하지 않았다.
- DeepRefine Docker 이미지 안에서 vendored atlas_rag 가 import 되는지. 이미지를 받지 않았다.
- EvolvingWorld open vs fixed schema 차이(1.25·1.35점)가 잡음보다 큰지. 유의성 검정을 찾지 못했다.
- graphify 가 `memory/query_*.md` 를 남기는 정확한 조건. graphify 저장소를 열지 않았다.
