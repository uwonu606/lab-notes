# llm-wiki 네 레포 커리큘럼 — 개요로 네 레포의 큰 구조를 먼저 보고, sage-wiki·jonex를 중심으로 기제 하나씩 견주는 단원 10개로 엔터프라이즈 llm-wiki의 결정 22개를 정한 뒤, 첫 뼈대를 한 바퀴 돌린다(단원 0~11)

이 커리큘럼은 회사 안 여러 사람이 쓴 보고서를 넣고 서로 잇는 엔터프라이즈 llm-wiki를 설계하려고 짰다.
0단원은 `overview.md`로 jonex·AutoSci·sage-wiki·GD4AI 네 레포의 큰 구조와 기능을 먼저 본다.
1~10단원은 단원마다 기제 하나를 다룬다. 기제는 "안에서 어떤 상태가 언제 바뀌는가"이고, sage-wiki와 jonex가 그 기제를 어떻게 다르게 풀었는지 견준다.

보고서를 읽는 범위는 #읽는 범위가 정한다. GD4AI는 세 절만 읽고, AutoSci는 개요로 갈음한다.

단원 순서는 보고서 한 편이 wiki를 지나는 길을 따른다.
경계(누가 정하나) → 원문 준비 → 같은 대상 → 근거 → 장부와 증분 → 연결 → 조회 → 사람 → 운영 순서다.
앞 단원의 실험 산출물을 뒤 단원이 입력으로 쓰고, 11단원은 그것을 이어 붙여 첫 뼈대를 만든다.

## 단원 하나가 도는 방식

단원 하나는 lab-notes 스킬의 회차 1~2개다.

1. 단원의 **회차 물음**에 대한 예측과 확신(높음/낮음), 그리고 "이 기제가 없으면 무엇이 깨질까"를 보고서·코드를 읽기 전에 `notes.md`의 `예측:`·`없으면:`에 쓴다. 건너뛰면 `건너뜀`이 적힌다. 3에서 실험을 고른 뒤, Claude는 그 실험 출력에 맞춘 예측을 한 번 더 받을지 묻는다.
2. **읽을 것** 표의 순서대로 보고서 절과 코드를 읽는다. 마지막 줄은 개요 문서 #차용 지도의 해당 절이다. 읽은 절 목록은 `notes.md` 그 회차의 `실험:` 줄 앞에 `읽음:` 한 줄로 남긴다.
3. **실험 후보** 하나를 `lab/NN-이름/`에 만들어 돌리고, 예측과 결과를 견준다. 코드를 가리고 기제를 내 말로 설명한다. 여기까지가 lab-notes 회차다.
4. **생각 물음**에 답한다. 답은 `my-thinking.md` #생각 기록에 낱말 그대로 남는다.
5. 단원의 결정에 지금 입장이나 `미정`과 그 이유를 `my-thinking.md` #지금 입장에 적는다.
6. `checklist.md`의 그 단원에 체크한다.

입장은 그때의 근거로 세운 가설이다.
뒤 단원에서 근거가 흔들리면 그 결정과 그 위에 선 결정을 다시 열고, 다시 연 이유를 `my-thinking.md`에 적는다.

## 실험 규칙

- 레포 코드는 읽기만 하고 실행하지 않는다. 보고서가 가리키는 기제를 Python 표준 라이브러리로 수십 줄에 다시 만든다.
- 실험 폴더는 `lab/NN-이름/`이고 NN은 단원 번호다. `lab/repos/` 안에서는 아무것도 만들지 않는다.
- 입력은 #실험 문서 묶음의 가짜 사내 보고서다. 진짜 사내 문서는 쓰지 않는다. 단원마다 복사하지 않고 `lab/00-corpus/`를 경로로 읽는다.
- 앞 단원 산출물을 입력으로 쓰는 실험은, 그 산출물이 없으면 `truth.json`에서 바로 입력을 만든다. 앞 실험이 늦어져도 뒤 단원이 막히지 않는다.
- 한 run에서는 하나만 바꾼다. 두 run이 다르면 무엇 하나가 달랐는지 실험 폴더 `README.md` 첫 줄에 적는다.
- 출력에는 결과만이 아니라 숨은 상태(점수, 후보 창, 버린 항목과 이유, 장부 줄, 사건 순서)를 찍는다.
- 실험마다 아래 단원에 적힌 "성공"을 돌리기 전에 `notes.md` 그 회차의 `실험:` 줄 끝에 `· 성공: …`으로 옮겨 둔다.

### 로컬 Ollama 모델

LLM과 임베딩은 로컬 Ollama(`http://localhost:11434`)의 아래 다섯 모델만 쓴다. 다른 모델이나 외부 API는 쓰지 않는다.

| 모델 | 쓰는 곳 |
|---|---|
| `exaone3.5:2.4b` | 생성. 한국어 추출·판정의 기본으로 쓰는 가장 작은 모델 |
| `gemma4:e2b-it-qat` | 생성. 같은 실험을 다른 작은 모델로 다시 돌려 견줄 때 |
| `llama3.1:8b` | 생성. 작은 모델의 한계를 가를 기준선으로만 |
| `bge-m3` | 임베딩. 이름·조각 유사도의 기본 |
| `nomic-embed-text` | 임베딩. bge-m3와 견줄 때 |

- 생성은 `POST /api/chat`이나 `/api/generate`를 `"stream": false`로, 임베딩은 `POST /api/embed`를 `urllib.request`로 부른다.
- 구조화 출력은 `format`에 JSON schema나 `"json"`을 넣는다. 둘 다 실패할 때의 사다리는 1단원 실험이 정한다.
- 재현용 생성 호출은 `options.temperature` 0과 고정 `seed`로 부른다. 이 설정에서는 같은 입력을 3번 돌려도 거의 같은 출력이 나와서 갈림을 잴 수 없다.
- 갈림을 보는 실험(`lab/02-coverage-gate/`, `lab/04-two-vs-three/`)은 temperature 0.7에 seed를 1·2·3으로 바꿔 3번 돌린다. 두 설정의 결과는 따로 찍는다.
- 생성 호출은 `"think": false`로 부른다. `gemma4:e2b-it-qat`는 기본 호출에서 생각 글이 출력 토큰을 다 써서 `message.content`가 빈 채로 `done_reason: length`가 나온다(2026-10-11 검증 때 `/api/chat`, `num_predict` 200으로 확인).
- 결과에 모델 이름, temperature, seed, 프롬프트 해시, 응답의 `done_reason`을 함께 찍는다. `done_reason`이 `length`인 응답은 파싱 실패와 따로 센다.
- 긴 입력은 `options.num_ctx`를 입력 길이에 맞추고, 응답의 `prompt_eval_count`로 입력이 잘리지 않았는지 본다.
- 0단원에서 `curl -s localhost:11434/api/tags`로 다섯 모델이 보이는지 확인한다. 임베딩 둘은 `bge-m3:latest`, `nomic-embed-text:latest`로 찍힌다.

## 실험 문서 묶음

0단원에서 `lab/00-corpus/`에 한 번 만들고 모든 단원이 다시 쓴다.
작성자 4명(부서 둘 이상)이 쓴 보고서 8~10편이다. 대부분은 한 편 300~1,500자이고, 주제가 섞인 긴 문서 2~3편만 5,000~20,000자다.

짧은 문서만 있으면 조각 기준 대부분이 문서 하나를 조각 하나로 만들어 기준끼리 견줄 수 없다(sage-wiki 조각기는 token 상한 이하이면 문서 전체를 조각 하나로 둔다, `sage:internal/extract/extract.go:176-181`).

Claude가 아래 함정 표대로 보고서 초안과 정답 파일을 쓴다. LLM으로 보고서를 만들지 않는다. 사용자는 우리 회사에서 실제로 쓰는 별칭 꼴(0단원 생각 물음 1의 답)을 한 편 이상에 넣으라고 고친다.

| 심을 것 | 예 | 시험하는 단원 |
|---|---|---|
| 같은 대상, 다른 이름 | "3호기 증설" / "P3 라인 확장" / "삼호기 증설 과제", "고객관리시스템" / "CRM" | 3, 4, 7 |
| 같은 이름, 다른 대상 | 영업팀의 "알파 프로젝트"와 연구팀의 "알파 프로젝트" | 4, 7 |
| 번호·차수만 다른 대상 | "2차 과제" / "3차 과제", "2025 계획" / "2026 계획", "초안" / "최종" | 3, 4 |
| 관계지만 같지 않은 대상 | 구 제품명 / 신 제품명, 모회사 / 자회사, 상위 과제 / 하위 과제 | 4, 7 |
| 두세 글자 사내 약어 | "AP", "QA팀"처럼 짧아서 글자 대조가 불안한 이름 | 3 |
| 형식 없는 문서 | heading 없는 메모, 표만 있는 주간보고, 참석자 명단이 긴 회의록, 파일 이름이 날짜뿐인 문서 | 2, 8 |
| 긴 혼합 문서 | 주제 3~4개가 섞인 5,000~20,000자 회의록·주간 종합 보고서 2~3편. 주제 경계를 `topic_spans`에 단다 | 2, 7, 8 |
| 페이지가 되면 안 되는 이름 | 회의록 참석자, 표 머리글 약어, 나열·괄호 속에만 나오는 이름 | 2 |
| 바꿔 말한 사실, 숫자 왜곡 미끼 | 원문 숫자를 풀어 쓴 문장, "15만 원"이 든 문장, "오프라인 배포를 지원하지 않는다" | 1, 5 |
| 수치 충돌 | 같은 지표를 두 작성자가 다르게 적고, 한 편은 남의 말을 전한다 | 5 |
| 개정본 | v1에 있던 사실 하나가 v2에서 빠진다. 같은 사실을 다른 작성자도 적는다 | 6 |
| 문서 권한 | 한 편만 "제한" 등급이고 부서 A만 본다 | 9 |
| 용어가 다른 연결 | 서로 인용하지 않고 이름도 다르지만 같은 일을 다루는 두 보고서 | 7, 11 |
| 문서 번호·과제 코드 참조 | "PRJ-2026-031 참고", "QA-118 건"처럼 결정적 키로 다른 문서를 가리키는 문장 | 7 |

정답과 메타데이터는 세 파일에 둔다. 위치(`start`, `end`)는 손으로 세지 않고 `check.py`가 원문에서 찾아 채운다.

| 파일 | 모양 |
|---|---|
| `docs.json` | `[{doc_id, file, author, dept, version, supersedes, access}]`. 형식 없는 문서는 머리말이 없으니 작성자·부서·판·권한은 여기에만 있다 |
| `truth.json` | `same_pairs`, `diff_pairs`, `numbered_pairs`, `relation_pairs`, `undetermined_pairs`, `link_doc_pairs`, `key_link_pairs`, `page_names`(이름, 페이지가 될지, 이유), `facts`, `conflicts`, `topic_spans`, `traps`, `questions` |
| `glossary.json` | 사람 용어집. `{정식 이름: [별칭]}`. 같은 대상 쌍 하나는 일부러 빠뜨린다 |

`truth.json`의 항목 모양은 이렇다.

- `facts`, `traps`, `topic_spans`의 항목은 `{doc_id, start, end, text}`이고, `traps` 항목에는 함정 표의 행 이름을 `trap` 칸에 단다.
- 쌍 항목은 `{a, b, trap}`이다. `a`·`b`는 이름이거나 `doc_id`다.
- `questions` 항목은 `{q, answer_spans[], needs_holdout, answerable}`이다. 묶음에 답이 없는 질문 하나는 `answerable: false`다.

11단원용 보고서 2편은 `lab/00-corpus/holdout/`에 따로 두고 11단원 전에는 어떤 실험에도 넣지 않는다. holdout이 필요한 질문은 `needs_holdout: true`로 표시한다.

뼈대는 앞 단원 실험을 이어 붙인 것이다: 추출과 거부(1단원), 조각과 위치(2단원), 후보와 판정 사다리(3·4단원), 근거 gate(5단원), 사실 장부(6단원), 연결 후보(7단원), handle 인용 조회(8단원), 쓰기 함수 하나와 승인 대기열(9단원), 호출 장부와 원자 발행(10단원).

**성공으로 보는 것**

- 용어집만 고친 재실행에서 추출 LLM 호출이 0이다.
- 지운 보고서만 받친 사실은 철회되고 다른 보고서가 받친 사실은 남는다.
- 0단원 `baseline.json`과 같은 질문의 답을 견준 표가 있다. holdout 질문은 baseline을 한 번 더 돌려 견준다.
